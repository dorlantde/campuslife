## 1. 已知事实与能作的判断

| 项目 | 已确认事实 | 当前判断 |
|---|---|---|
| 原RabbitMQ探针 | components.yaml串行执行check_running与check_port_connectivity；interval/timeout各5秒，retries30，start_period15秒；compact4g继承该探针 | 5秒预算覆盖两个独立CLI调用；具体每个调用的耗时、进程生命周期和资源争用未采集 |
| 已观察异常 | D.6i出现unhealthy/连续40次失败，最近五次退出-1且有超时标志；重启后healthy仍观察到10/17次失败 | 不能将超时直接解释为Broker停止、凭据错误、OOM或一定是探针误报 |
| 实际业务 | 同轮两次领券实际消费成功，资源与私有观测钩子通过 | 消息链在相应时点有效，不证明持续健康或最大容量 |
| SSH重置 | 本机原回执为空，原监督和case进程仍存活；从同一stage取回exit0结果 | 传输结果与任务结果应分别判断，具体网络/宿主原因未定 |
| 最近资源审计 | D.6i结束后容器/卷/测试网络和生成秘密为空，三份release保留 | 这是上轮时间点的审计；本轮未重新查询实时云端状态 |

RabbitMQ 4.3 CLI手册说明：check_running检查应用是否运行；check_port_connectivity检查监听端口能否接受TCP连接，不执行消息协议握手或认证。因此这些检查本来也不能代替实际发布/消费验证。[4.3 CLI手册](https://www.rabbitmq.com/docs/4.3/man/rabbitmq-diagnostics.8)

当前官方监控说明指出CLI加入/退出Erlang distribution会产生探针开销；这支持评估频繁CLI的成本，**不构成本机超时根因证明**。本轮读到该监控页面为4.4版，4.3监控/HTTP页面未通过工具读取，不能据当前文档承诺固定4.3.6镜像的具体工具或端点兼容性。[官方监控说明](https://www.rabbitmq.com/docs/monitoring#health-checks-as-readiness-probes)

## 2. 探针专项：条件项，先验证再决定修改

推荐在需要依赖该健康状态开展正式云端测量时，先做**一次有界、单RabbitMQ的原探针专项**，不直接替换探针或增加5秒预算。

| 内容 | 拟议范围与完成标准 |
|---|---|
| 夹具 | 原固定4.3.6-management镜像、自有虚构凭据和临时数据；640MiB/no-swap、CPU0/1；不开公网，不连接真实业务库 |
| 样本 | 空闲及有限资源竞争两种窗口，各5次原组合探针；每个窗口各一次分拆的两条CLI用于定位耗时。一次记录完毕，不挑选“最好一轮” |
| 竞争窗口 | 只使用已有镜像中经核对的有界工作进程，最多60秒，记录CPU/内存；不安装压力软件，不冒充真实业务负载或重现全部D.6i条件 |
| 记录 | 实际配置、耗时/退出码/超时阶段、CLI是否正常退出和是否遗留子进程、Broker状态及cgroup/OOM；不输出cookie、密码、环境全集或任意诊断原文 |
| 时间与停止 | 整项建议上限480秒（含清理），每次原探针仍5秒；异常OOM、归属不明或无法安全清理则停止。没有解释力就报告未定因，不自动加样本/预算 |
| 交付 | 能区分节点故障、CLI调用成本及尚未解释的情况，列出证据和限度；诊断得到“未定因”也允许专项结束，不承诺必然找到根因 |

若原CLI成本确实影响检测，候选是**本机管理HTTP就绪检查与AMQP端口连接检查的组合**。当前官方HTTP文档的ready-to-serve-clients涵盖节点服务状态、AMQP监听及连接上限，但不能代替AMQP认证或消息消费，检查范围也不保证与原命令逐字等价。[HTTP API说明](https://www.rabbitmq.com/docs/http-api-reference#health-check-endpoints)

此候选尚未选定/验证：必须先核对固定镜像是否包含可用客户端、相应端点和权限；不能假设curl存在或在线安装工具改变固定镜像。当前Rabbit容器没有挂载RABBIT_OPS_PASSWORD，如果候选需要该秘密，应在具体实施提案中明确只增加到Rabbit容器，仍不交给app或映射管理端口，不把凭据放进argv/日志。没有这些验证就保留原配置。

采纳任何候选前，应验证正常可用、应用/监听不可用、错误认证、超时和恢复，确认不是“HTTP响应就算健康”；保留原5秒外层上限，拒绝停用探针、删掉失败检查或无限放宽预算。若需要改变检测语义、频率、秘密挂载或预算，先提交具体差异再讨论。本轮没有批准这种改变。

## 3. 断线回执：区分传输、任务与清理

推荐后续M06.2长时运行器具备“显式启动、按case查询、取回同case结果”的最小能力。沿用现有远端结果文件，不搭建任务平台或常驻守护服务。

- 启动前形成新case目录和输入摘要；记录启动标识、PID/进程组、进程启动时间、批准的绝对截止和自有资源清单。
- 监督进程与测试stdio从SSH会话分离；继续执行原任务预算及有界清理，结果通过临时文件后原子发布。此分离是待实现能力，D.6i只证明了那一次断线后原监督仍存活。
- SSH非零、空输出或未知受理结果时，查询原case，不能直接重新启动。核对远端回执中的case、输入摘要、任务退出码、断言及清理结果后才报告成功。
- 需要发信号或清理时，核对PID启动标识/预期命令及资源标签，防止PID复用或误删；监督不可证明存活时进入受控处理，不假设任务已失败或无限等待。
- 保留原传输错误及恢复结果两份证据；不修改SSHD、云安全组或已有SSH keepalive参数来宣称修复未知根因。

完成标准是用无业务数据的短任务覆盖成功、任务失败、结果传输中断后的同case取回、超时与准确清理、重复查询不重复执行；测试每个case只启动一次。不为此再运行优惠券或打印整链。具体运行器实现随M06.2的批准预算定稿，本轮只提出要求。
