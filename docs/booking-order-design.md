# 预约订单第一步：待支付暂占与释放（已确认方案）

- 日期：2026-10-22（Asia/Shanghai）。
- 状态：用户已选择“采用并实现”；决定见 [ADR-0022](decisions/0022-booking-orders.md)，实际执行及人工步骤见[验收指南](booking-orders.md)。
- 依据：[业务基线](decisions/0001-v1-baseline.md)、[状态与事务草案](v1-state-transitions.md)、[数据库草案](v1-database-design.md)、[接口契约](v1-api-contract.md)、[排班锁协议 ADR-0018](decisions/0018-merchant-schedule.md)、[候选阶段 ADR-0021](decisions/0021-booking-slot-candidates.md)。

## 1. 推荐交付范围

先形成“学生创建待支付预约 → 查看订单 → 主动取消或到期释放 → 时段可重新选择”的小闭环。支付、商家接单及履约分别后续实现，不把整个订单系统放进一项任务。

| 接口 | 推荐本轮行为 |
|---|---|
| POST /api/v1/orders/bookings | 正常 STUDENT 创建本人待支付预约；首次 201，幂等重放 200 |
| GET /api/v1/orders/{orderId} | 正常 STUDENT 查看本人订单；他人订单与不存在统一 404 |
| POST /api/v1/orders/{orderId}/cancel | 仅处理本人未支付预约；成功返回当前详情 |
| 已有 GET /api/v1/shops/{shopId}/booking-slots | 接入真实占用排除，保持已有参数、资格和响应结构 |

另实现数据库驱动的未支付超时关闭，以及影响预约的配置变更保护。订单列表、事件查询、支付、退款、商家订单入口、打印订单和评价本轮不开放。运行版预计 33 → 36 个操作，完整规划仍 62 个，剩余 26 个待开发。

## 2. 创建请求、时间与金额

沿用原 BookingCreate：serviceId、barberId、startAt、expectedServiceVersion、expectedPayableAmount，以及可选 note。不接收 studentId、shopId、endAt、status 或客户端单价；身份来自会话，店铺由服务确定，结束由服务时长计算。未知字段拒绝。

- ID 为规范正 BIGINT 字符串；服务版本为规范非负 BIGINT 字符串。
- startAt 必须含 Z 或明确时区偏移，转换为同一 Instant；校园日期为上海今天至第 6 天，校园起点为整 15 分钟，无秒/小数秒，不跨午夜。等价的 Z 与 +08:00 表达视为相同时间。
- 创建沿用公开理发资格、本店上架理发服务、人员启用及实际绑定；营业开关必须打开，完整区间须落在营业时间与当天排班内。店铺当前 openNow 不限制未来时段。
- 至少提前 2 小时，等于允许。写事务在获得相关锁后重新捕获服务端 Clock 判定时刻，并在提交前复查时间窗口与会话有效性；等待锁不会延长预约窗口。不同于只读候选查询的一次 Clock，写事务必须在等待后复核。
- 价格、时长与版本全部取当前配置。预期版本或金额不一致均为 409 QUOTE_CHANGED，不按新价格静默下单；价格快照为原价/应付金额，折扣 0、币种 CNY。
- note 省略或 null 归一为无备注；字符串去首尾空白，最多 300 个 Unicode 码点，空串归一为无备注。保留内部空白。
- 创建时间及 paymentDeadline 使用锁内最终通过校验的服务端毫秒时刻，paymentDeadline = createdAt + 15 分钟；首次订单 version="0"，创建事件 eventSeq=0。

首次成功状态为 PENDING_PAYMENT + NOT_PAID，占用为 HELD。保存店铺名、服务名、理发师名、单价、时长及来源服务版本快照；后续修改名称、价格或时长不会改写原订单。订单号由服务端生成并有唯一约束，不充当访问凭证。

创建错误约定：非法字段/时间表达为 400 VALIDATION_FAILED；资源不存在、服务/人员跨店或目标店铺不具备公开资格为 404 RESOURCE_NOT_FOUND。资源归属成立后，关店为 409 SHOP_UNAVAILABLE，服务下架或非理发为 409 SERVICE_UNAVAILABLE，人员停用或未绑定为 409 BARBER_UNAVAILABLE；日期窗口、提前时间、营业/排班覆盖不满足为 409 BOOKING_TIME_INVALID，真实占用冲突为 409 BOOKING_CONFLICT。严格格式验证先于重放，当前日期窗口/配置可售检查只针对新建。

## 3. 真实占用与防止重复预约

占用保存在 booking_detail，不再额外建立一套内容重复的占用表。沿用草案占用状态 HELD / ACTIVE / CONSUMED / RELEASED；本轮实际产生 HELD → RELEASED，其他状态仅保留后续支付/履约所需的定义，不伪造相应能力。

重叠条件为 existing.startAt < requested.endAt 且 existing.endAt > requested.startAt。相邻区间允许；同一开始时间的唯一索引不能代替区间判断。不同人员独立，同一人员同一天的相关写入在同一日期保护行内串行核验。

公开候选查询仍为只读 RR，在同一快照中排除 HELD、ACTIVE、CONSUMED 的重叠区间；即使 HELD 已超过支付截止时间，只要关闭事务尚未提交就继续保守占用。查询不负责清理或写状态，也不预留资源。创建必须重新检查，不能信任此前候选结果。

创建在店铺与日期锁内关闭本次请求区间重叠的已到期未支付暂占，再检查真实占用；同一事务内按订单 ID 升序处理。失败时所有写入一起回滚；后台关闭任务仍能独立完成释放。不得在锁外或基于旧 RR 快照作出“无人占用”的决定。

## 4. 取消、超时和重试

推荐使用以下明确边界：

| 情况 | 推荐结果 |
|---|---|
| 本人取消，仍待支付且 now < paymentDeadline | CLOSED / NOT_PAID / RELEASED，closeReason=USER_CANCEL |
| 本人重复取消，原因为 USER_CANCEL | 200，返回同一订单当前详情，不重写关闭时间或重复事件 |
| 本人取消时 now >= paymentDeadline | 提交 PAYMENT_TIMEOUT 关闭并释放，然后返回 409 PAYMENT_DEADLINE_PASSED |
| 已由超时关闭后再取消 | 409 PAYMENT_DEADLINE_PASSED，不改成 USER_CANCEL |
| 其他状态取消 | 409 ORDER_STATE_CONFLICT；已支付取消留待后续实现 |
| 详情读取已经到期但尚未关闭的待支付单 | 200，如实返回数据库状态和已到期 deadline；GET 不写状态、不宣称仍可支付 |

关闭时主订单 version 增加一次，并写同序号状态事件；SYSTEM 超时事件操作者为空，学生取消记录本人账号。没有支付流水，本轮不产生退款。

推荐使用 Spring 自带调度，每 30 秒扫描最多 100 个到期候选，按截止时间/ID 排序，每单独立事务；应用启动后立即进行首轮扫描。候选扫描不持订单写锁，实际关闭必须重新锁定并判断。多实例重复扫描允许，通过同一锁协议和状态条件确保仅关闭一次；失败记录订单 ID 和原因，后续扫描重试。暂不引入 Redis、MQ 或独立任务平台。

截止条件始终为 now >= paymentDeadline。后台扫描延迟不延长有效期；创建的锁内清理和取消自行检查期限。不要在写完关闭后直接抛出导致事务回滚的业务异常：事务返回结果，提交成功后由外层转换为 409。

### 创建幂等

Idempotency-Key 必填，1～64 个 ASCII 字母、数字、短横线或下划线，区分大小写；按学生账号 + CREATE_BOOKING + 键唯一。无效键为 400 IDEMPOTENCY_KEY_REQUIRED。请求摘要来自验证、归一化后的字段，包含两个预期报价字段及规范化时间/备注，不依赖 JSON 字段顺序。

- 相同键、相同内容：返回原订单当前详情，响应 200，带 Idempotency-Replayed: true；即使原单已取消/到期也不新建。
- 相同键、不同内容：409 IDEMPOTENCY_KEY_CONFLICT。更换选择或重新确认新报价时使用新键。
- 重放仍要求正常学生身份和原订单归属；确认存在已提交的同请求记录后，不重新按当前服务上下架、价格、日期及排班阻止重放。
- 业务失败不消耗永久幂等键。并发重复请求遇唯一约束竞争时，整笔回滚，再开新事务查询原结果，不能在已经失败的事务内继续。
- 死锁/锁超时整笔回滚，返回 503 SERVICE_TEMPORARILY_UNAVAILABLE；本轮不做未验证的自动重试，调用者可带原键重试。

## 5. 商家配置变更保护

不冻结全部商家配置。区分“新订单是否可售”与“已有预约是否还能按原计划履约”，推荐如下：

| 配置操作 | 推荐规则 |
|---|---|
| 手动停业、服务下架 | 只停止新订单，允许已有预约继续查看、取消及后续履约，不自动关单 |
| 修改店铺/服务/人员名称、说明，服务价格或时长 | 允许；已有订单始终用原快照，新订单用最新配置 |
| 停用理发师 | 该人员存在 HELD/ACTIVE 且 endAt > 锁内 now 的预约时，409 BOOKING_CONFLICT；先取消/处理再停用 |
| 删除某项人员服务绑定 | 该人员/服务存在上述未结束 HELD/ACTIVE 预约时，409 BOOKING_CONFLICT；未删除的绑定和新增绑定不受影响 |
| 替换或清空某日排班 | 新排班必须覆盖当天 endAt > now 的 HELD/ACTIVE/CONSUMED 原区间，不能裁剪、移动或拆开覆盖；冲突为 409 SCHEDULE_CONFLICT |
| 缩短每周营业时间 | 保留已有“覆盖今天及之后全部排班”规则，并校验未结束占用区间覆盖；冲突为 409 SCHEDULE_CONFLICT |

未提交关闭的过期 HELD 仍受保护，后台关闭完成后再重试配置。CONSUMED 不阻止停用/解绑，但在原结束时间之前仍阻止裁剪时段与重售。已结束但未处理的历史异常不永久阻塞未来配置，其订单和事件仍保留，不自动完成或删除。

本轮不新增暂停商家或停用账号入口，不替尚未定稿的管理员存量处置规则作决定。

## 6. 表、分层与锁协议

建议 V9 新增四张实际使用的表：service_order、booking_detail、order_event、idempotency_record。占用放在预约扩展中，不重复建表；不建立支付、退款、打印、评价或文件空表。字段以本提案及现有草案为基础在确认后完成 DDL：订单主表 + BOOKING 一对一扩展，金额/时间/状态约束、外键、订单号及幂等唯一约束、查询与到期扫描索引。

新增 order 业务模块，按 controller/service/dto/vo/entity/mapper 分层；占用/订单状态归订单模块，merchant 配置调用必要的预约保护查询。避免 merchant 反向依赖订单 HTTP 层，也不把订单塞进商家服务。沿用 MyBatis-Plus 与注解 SQL，不加 XML 或新框架。

遵守 ADR-0018，写事务采用 RC：

1. HTTP 写操作按现有账号 → 当前会话顺序验证/协调身份；SYSTEM 关闭没有登录身份锁。
2. 预约创建/取消/超时先店铺 S（FOR SHARE），再日期保护行 X，再配置/订单资源。定位店铺/日期可以先普通查询，锁后重新核对归属及状态。预约仅使用已有且合法排班对应的保护行，不在不存在的日期上伪造可用性。
3. 商家配置先店铺 X，枚举需要保护的日期行按人员/日期升序取锁，再读取/锁定人员、关系、排班或订单；调整旧人员/服务配置路径，使其不会在持有后续资源后反向申请日期锁。
4. 持店铺锁期间禁止再反向锁经营账号，防止与商家“账号 → 店铺”的既有入口形成相反顺序。经营资格核验和后续账号停用能力须遵守同一协调规则，不提前新增账号停用接口。
5. 同类多订单按 ID 升序；事务内不做外部 HTTP、支付或消息发送。快照、主/扩展、事件和幂等成功记录一起提交或回滚。

店铺 S 允许不同人员/日期的预约并行；配置店铺 X 会等待相关交易，正确性优先。不能仅凭注解或 mock 宣称无重复预约，必须验证真实 MySQL 并发与锁等待后的重新判断。

订单详情沿用统一 OrderDetail 方向：保留类型、金额、状态、期限、关闭事实及 booking 快照；尚未发生的时间和 payment/refund/printing 为 null，reviewed 为 false 并说明评价未实现。不能伪造已支付流水。具体 DTO、索引和 SQL 属于已批准范围内的实现细节，但不得悄悄加入新的状态转换。

## 7. 完成标准与人工验收

本次确认的实施范围按第 1 节完成，不顺带开放支付、商家履约或其他模块。

- 真实 MySQL 验证多学生竞争相同/交叠区间只有一单有效；相邻区间和不同人员不误冲突。同键同内容只有一单，不同内容冲突。
- 验证金额/版本变化、UTC 与偏移量等价、严格网格、日期/2 小时边界及锁等待跨界；身份过期、跨学生/跨店和不合法资源不写入。
- 验证取消/超时/新建竞争、重复扫描与应用重新扫描、关闭事件仅一次，以及释放后可重新下单。验证事务提交后的超时 409 确实已经关闭。
- 验证停用、解绑、排班/营业时间修改与创建竞争，成功订单总能被最终配置及原快照解释；失败的配置写不递增版本。
- 在主订单、扩展、事件或幂等写入后注入失败，检查全事务回滚、无半笔订单/残留占用；不把纯内存或 mock 结果当作 InnoDB 锁验证。
- 同步 Swagger、运行 OpenAPI、完整规划和点击指南；尚未实现支付的阶段在接口说明中明确可达状态，创建后的 OrderDetail 不假称完整订单生命周期已交付。

人工流程：用商家准备两个相邻候选 → 学生 A 创建并记录订单 ID/幂等键 → 匿名候选不再显示重叠选择 → 学生 B 相同区间收到 409 → A 重试原键得到同一单 → A 取消 → 候选重新出现 → 使用新键再次创建。另等待 15 分钟及一次扫描查看超时关闭；精确时间、重启恢复和并发用例由注入 Clock 的自动化验证覆盖，无须修改电脑时间。

本方案保留规则与完成标准，实际测试结果以[验收指南](booking-orders.md)记录为准，人工验收未代用户执行。
