# M02.1：公开商家详情评分缓存方案（已确认）

日期：2026-10-28。状态：用户已明确**采用并实现**。下文保留方案提出时的比较、建议和验收计划；其中“当前/尚未/本轮仅设计”指设计阶段，不代表最新进度。后续M02.2已实施，实际代码、V16/24表、运行与验证范围以[使用指南](redis-rating-cache.md)、[ADR-0048](decisions/0048-public-rating-cache.md)及[验收报告](reports/redis-rating-cache-2026-10-28.md)为准，未测量的性能收益仍不能宣称完成。

## 1. 推荐范围与业务依据

先只优化`GET /api/v1/shops/{shopId}`中的**全部VISIBLE评价的评分总和与数量**。它们是相同店铺反复浏览时可复用的统计；平均分仍按原BigDecimal除法、两位HALF_UP计算，没有公开评价仍为null/0。

依据[C06实测](reports/public-shop-query-baseline-2026-10-28.md)：热门店5,020条评价中4,518条可见，详情资格/营业时间访问少量记录，而SUM/COUNT扫描4,518条；单聚合SQL中位3.29 ms，完整详情中位7.29 ms。这是已有合成数据证据，不是线上流量或缓存收益。普通店的聚合便宜，增加Redis访问可能没有收益，后续必须保留这组对照。

保留MySQL中的公开资格、店铺/分类资料、营业时间；openNow仍取本次Clock按上海时区现场计算。列表保持M01实际SQL及原批量评分，公开评价分页保持原作者当前昵称/可见性快照。本人/商家/管理员、订单、支付、文件和预约占用不读此缓存。只做一个真实读场景，不顺带缓存整个目录、账号权限或候选时段。

## 2. 方案比较与选择

| 方案 | 代价与问题 | 建议 |
|---|---|---|
| 整个详情按shopId缓存，TTL＋写后删除 | 资料/营业状态/评分可能来自旧时刻，资格停用还须单独复核；删除失败和旧请求回填均有窗口，不能继续宣称整个响应同RR | 暂不采用 |
| 评分接受例如30秒陈旧，TTL＋写后删除 | 实现较少，但明确改变ADR-0043和接口的快照承诺；需处理老快照晚回填，不是设置TTL就自动有30秒上界 | 可讨论的更简替代，本案不推荐改变已验收语义 |
| 营业时间按已有shop.version缓存 | 可保留原RR，几乎不动写流程；但主要省一次很小的范围查询，没有解决当前测到的热点聚合 | 次选，不同时实施 |
| **评分统计按MySQL统计版本缓存** | 增加一张小的技术元数据表，提交/隐藏评价各多一次原子版本更新；命中仍要读取MySQL资格及版本，但可跳过整店评价聚合 | **推荐**：保留原读取语义，验证Redis收益与维护成本 |
| MySQL直接维护SUM/COUNT | 同样可避免扫描，但这是持久聚合优化，不是Redis缓存方案 | 后续替代方案，不同时叠加到本轮 |

不能用已有`shop.version`充当评分版本：当前提交或隐藏评价不会修改它；它还承担经营配置的并发确认。也不应把每次评价变成shop S→X升级，导致经营配置版本无故变化及新的锁竞争。

## 3. MySQL统计版本与写入协议（建议V16）

新增`shop_rating_revision`，只有`shop_id`主键/外键和正BIGINT `revision`，不保存SUM/COUNT、评价内容或缓存数据。无行视为虚拟版本0；第一笔评价提交创建版本1，之后每次真实统计变化递增。版本用于标识公开评分集合，不作为新的对外业务版本。

升级时，为**已有任意评价（包括全部隐藏）的店铺**回填revision=1；无评价店铺维持无行。迁移不重新计算或改动评价事实。部署实施时需核对无并行旧应用写入的迁移窗口；回填后旧应用不能继续绕过版本协议写评价。实施后预期V1～V16、24张应用表（原23＋1张技术元数据），此刻尚未创建。

| 实际变化/操作入口 | 统计版本动作 | 不变的业务事实 |
|---|---|---|
| `OrderReviewTransactions.create`首次成功插入VISIBLE评价 | 在同一原RC事务内原子创建/递增一次 | 一单一次、评分/文字、订单版本与事件规则保持 |
| `OrderReviewTransactions.hide`首次VISIBLE→HIDDEN | 在同一原RC事务内原子创建/递增一次 | 首次审核人/原因/时间规则保持 |
| 同管理员同原因重复隐藏，重复评价被拒绝，其他校验失败 | 不递增；若后续失败则随整个事务回滚 | 原重放/409和身份复核规则保持 |
| 作者改昵称/停用、商家经营资料/营业开关/时段/审批/成员变化 | 不递增 | 作者状态不决定评价是否统计；店铺资格/展示字段从本次MySQL快照读取 |

版本维护**独立于缓存开关和Redis是否可用**。否则关闭缓存期间的变化会在再次开启时命中旧键。版本写失败必须回滚评价业务事务；不能吞掉异常后提交评价，这个MySQL依赖与可降级的Redis写入不同。BIGINT达到上限拒绝变更并回滚，不回绕/重置版本。

沿已有锁序，在持有店铺S及订单/评价写锁后，最后原子upsert统计版本；不升级shop锁、不反向锁其他账号、不在拿到版本锁后再请求其他订单/评价锁。create为账号→会话→店铺S→订单/新评价→统计版本；hide为管理员账号→会话→店铺S→评价→统计版本。版本更新后仅做现有内存会话期限复核与返回。多笔同店评价会竞争这一行，这是明确增加的写成本，需真实MySQL并发验证，不宣称永不死锁。

不在业务写事务中访问Redis，也不引入MQ、重做订单事务或添加通用事件框架。手工SQL绕过版本协议不在正确性保证内；测试造数/运维修复若直接写评价，必须同步维护版本。新增评分修改、恢复或删除评价入口时也必须接入协议，当前这些入口不存在。

## 4. 缓存数据与键

建议键形状：`campuslife:<datasetNamespace>:rating:s1:<shopId>:<revision>`。数据为小型显式JSON：schema、shopId、revision、ratingSum、reviewCount；ID/版本/精确整数用规范字符串表示，统计精确到整数，不缓存浮点平均分或完整响应。仅接受同店同版本、非负计数、合法评分总和的已知schema，限制载荷大小；非法JSON或字段不匹配当作未命中，从MySQL重建。

正统计TTL随机300～360秒；无公开评价也缓存明确的sum=0/count=0，TTL随机30～45秒。它是有效店铺的真实空统计，不是“店铺不存在”哨兵。使用单条带过期参数的SET NX，避免SET成功但EXPIRE未执行的永久键；已存在键不反复续期。随机TTL分散批量到期，但不承诺消除所有并发回源。[Redis SET及过期选项](https://redis.io/docs/latest/commands/set/)

`datasetNamespace`须区分数据集、开发和测试环境。开启缓存前生成并保存本机专用命名空间；隔离测试使用随机前缀。恢复旧数据库、重建同名库/复用ID时更换命名空间，避免历史revision被重用；正常应用重启保持它。不得对共用实例执行FLUSHALL/FLUSHDB；历史键依靠TTL/淘汰回收。

## 5. 读取、回源与事务边界

只为detail新增读编排及独立的短RR读取组件，避免同类自调用使事务失效。其它列表/评价/服务查询不改为先后两个数据库快照。

1. 先按原规则校验shopId。开启缓存的详情查询在**一个只读RR事务**中读取公开资格/展示行，并LEFT JOIN统计版本，无行得到0；不可见直接404，不查询/写入Redis。
2. 在同一RR内读取营业时间、用本次Clock计算openNow。按该快照的shopId/revision读取Redis，严格验证小载荷；仅使用完全匹配的统计。
3. 命中跳过`PublicReviewMapper.ratings`；未命中或Redis异常，在**这个原RR事务内**调用原聚合查询，不能启动另一个事务读取“更新的评分”。将本次快照结果与待回填键带出事务。
4. 数据库读事务成功返回后，外层编排再尝试SET NX＋TTL；数据库失败不回填。Redis回填失败不改HTTP成功结果；业务错误不被改成缓存错误。回填发生在数据库事务外，减少数据库连接持有时间。

命中预计2条业务查询（资格/版本联表、营业时间），未命中3条（再加聚合），不增加一个单独版本SQL。关闭缓存走原3查询路径。认证过滤器如有token，其查询另计；不能拿三条业务SQL声称整个请求完全不查数据库。

读取缓存发生在短RR事务内，是本案保留同快照、避免额外资格/版本往返的取舍；必须配置短超时与快速绕过，不能默认等待客户端长超时。返回前的数据仍来自本次数据库快照，不是“响应发出时的绝对最新状态”：并发停用后新快照返回404，之前已取得合法快照的请求仍可完成，与V1一致。

## 6. 一致性、失效与并发回填

不依赖提交后DEL保证正确性。**评价事实和统计版本同事务提交，就完成旧版本缓存的逻辑失效**；新快照只能选择新版本键，旧键物理存在不影响新请求。TTL主要控制内存，不能代替版本协议。首轮不再为旧键建立删除重试表或MQ补偿链。

| 竞争/失败 | 结果与理由 |
|---|---|
| 读请求取得r7，写事务提交r8，旧请求随后回填 | 只写r7键；新快照只选r8，不能被旧回填覆盖 |
| 旧RR请求在写提交后才从Redis读r7 | 合法：r7数据仍对应它的旧快照；不能强行混入r8统计 |
| 新评价或隐藏回滚/会话到期 | 评价和版本一起回滚，不产生已提交新集合 |
| 隐藏成功但Redis断开 | 版本已递增；后续新快照读新键，未命中从DB得出隐藏后的真实统计 |
| Redis丢失所有键/重启/内存淘汰 | 全部可回源，不丢评价事实；按当前DB版本重建 |
| 只有缓存键存在，MySQL资格读取失败 | 不凭缓存授权或返回详情，保留数据库错误边界 |
| 缓存回填响应丢失/重复回填 | 同一个不可变版本的结果相同，SET NX重复不改变业务事实或续期 |

核心不变量：相同数据集、店铺和版本只对应一个统计集合；任何影响统计的已提交变更都推进版本。版本保证必须由两个真实写入口及迁移测试验证，不能仅靠Redis测试证明。它保留逻辑同RR语义，但Redis本身并不参加MySQL快照或跨库原子提交。[Spring Data Redis事务说明](https://docs.spring.io/spring-data/redis/reference/redis/transactions.html)

热点未命中采用**实例内、按店铺＋版本合并在途加载**，不新增Redisson或分布式锁：最多256个在途键、等待最多20 ms，拥有者在请求线程同步执行原DB读取，无自建后台加载线程池。成功事务返回后先发布相同版本结果给等待者，再尝试Redis回填；失败则通知等待者并释放登记。等待超时或在途登记已满时，在自己的原RR内正常回源，不无限等待/排队；所有路径最终移除登记和释放名额。合并结果只允许同数据集/店铺/版本复用。

这只能减少当前单实例健康热点的重复查询；Redis停机、线程等待超时、不同版本或多实例时仍可能多次聚合。不能将“未命中合并”宣称为分布式互斥或保证100个并发只查一次。随机TTL＋有界合并＋故障绕过各自承担不同作用，不添加多级本地持久缓存。

## 7. 选型、本机环境与故障策略

- 客户端推荐`spring-boot-starter-data-redis`＋Lettuce＋StringRedisTemplate/明确JSON。现有Boot4.1.1本机BOM已核对管理Spring Data Redis4.1.1、Lettuce7.5.2.RELEASE；沿BOM，不另行钉冲突版本。当前POM尚未添加starter，也未完成真实连接/序列化兼容测试。选择显式版本键/回源编排，首轮不同时引入Spring Cache注解、Redisson和Lua。[Boot官方Redis接入说明](https://docs.spring.io/spring-boot/reference/data/nosql.html)、[RedisCache默认行为](https://docs.spring.io/spring-data-redis/reference/redis/redis-cache.html)
- 服务端建议官方Redis Open Source 8.2稳定分支，固定补丁标签和镜像digest；8.2.4可作为实施时核对的候选，不用latest。本案仅用GET和SET NX EX等基础命令，不依赖8.4新增条件语法。正式补丁/镜像拉取及Lettuce兼容性在M02.2实测记录，不在本轮伪造已安装。[官方发布目录](https://download.redis.io/releases/)、[官方安装说明](https://redis.io/docs/latest/install/install-redis/)
- 本机已发现Docker/WSL命令；读取Docker服务版本返回Linux Engine命名管道不存在，**尚未验证容器运行环境可用**。建议实施时使用Docker Desktop Linux容器，单独缓存实例只绑定回环地址。现在不自动启动Docker、安装WSL或改变当前MySQL/VS Code配置。
- 缓存默认关闭；关闭时不要求Redis在线或启动时PING，普通web-only测试不连接Redis。开启时连接/命令超时建议初始分别200/50 ms，单请求不重试Redis命令。发生连接/读写错误后实例绕过5秒，再仅放行一个恢复探测，其余继续DB；失败重新绕过。实际等待时间需测试，不能把配置值当端到端硬上界。
- Lettuce断连期间拒绝新命令、待处理请求队列有界（建议256），不让超时请求在后台无限积压或由每次HTTP触发重连循环。缓存开启但Redis离线也应允许MySQL正常的应用启动并降级；避免强制预热连接/PING成为启动前置。编解码使用项目Jackson3的显式DTO/字段，禁用多态默认类型和Java原生对象序列化；这些均需实际兼容验证。
- 本轮Redis仅保存可丢弃缓存，可配置128 MiB及allkeys-lru、关闭持久化；重启后重建。未来优惠券的受理/库存状态不能直接继承这套可淘汰、无持久化设置，应在M08重新隔离/定稿。当前不建立Redis集群或高可用承诺。
- 测试自建临时MySQL、专用随机命名/端口的Redis和命名空间，不扫描或清理已有容器/项目数据库；成功后只清理本次自有资源。用户密码、JWT、PDF及个人资料不存此缓存。
