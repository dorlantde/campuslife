# M05.2批次B：商家入驻、审核与经营配置

2026-10-29，按[已确认方案](minimal-frontend-design.md)和[ADR-0049](decisions/0049-minimal-frontend.md)交付。与[批次A](frontend.md)共用登录、会话、公开目录和请求层，本批只接已有V1接口，不新增后端规则/迁移/接口。验收证据见[报告](reports/frontend-batch-b-2026-10-29.md)。

## 页面入口

正常启动仍为：原VS Code配置启动后端，另开终端运行`scripts/frontend.ps1 -Action Run`，打开127.0.0.1:5173。密码和JWT只在原后端本机配置，不填到前端工程。

| 身份 | 入口 | 可用操作 |
|---|---|---|
| 未登录 | 顶栏“商家入驻”或登录页“商家申请入驻” → `/apply` | 独立创建商家账号与店铺申请；不把已有学生转换为商家，成功不自动登录 |
| MERCHANT | 顶栏“店铺管理”或工作区卡片 → `/merchant/shop` | 查看当前入驻结果/原因；被拒重提；批准且店主有效后显示配置页签 |
| ADMIN | 顶栏“入驻审核”或工作区卡片 → `/admin/shops` | 按状态筛选/分页查看申请，进入详情后批准或说明原因拒绝 |

管理员账号继续通过原本机`init-admin.ps1`流程显式初始化，不提供公开管理员注册或正式库默认账号。已有登录账号若需提交新的商家申请，先退出该账号。

## 一次完整点击流程

1. 未登录时提交商家账号、昵称、分类、店名、位置和介绍；成功显示店铺编号/待审核，再点“登录查看申请”。
2. 商家登录后可见待审核状态，此时不能维护营业或服务。另开独立管理员标签页登录，进入“入驻审核”，选择待审核，核对店名/位置。
3. 管理员可填写拒绝原因并拒绝；商家点“重新读取店铺”查看原因，修改后“重新提交入驻申请”。管理员必须重新载入当前版本再批准。
4. 批准后商家重新读取店铺，显示有效店主与配置页签。批准保持营业开关关闭；先配置服务/价目或人员时段，再按需要开启开关。
5. 商家在“店铺资料”修改介绍或营业开关，“营业时间”完整保存整周安排；设置采用校园上海时间。公开目录会反映获批准店铺的最新资料；营业中仍不等于可下单。
6. 打印店创建服务、决定上下架后，到“打印价目”选择服务并读取，为勾选的规格设置元/印刷面单价与启用状态，再保存。
7. 理发店创建理发服务，在“理发师与绑定”创建人员及初始绑定；新人员默认停用，核对后单独启用。到“按日排班”选人、选日期、读取后维护时段。

独立标签页登录不同角色，各自保留会话；复制标签页可能复制初始存储，操作前核对账号。没有“无凭据切换角色”或自动管理员登录。

## 保存语义与失败处理

| 表单 | 保存范围 | 必须理解的边界 |
|---|---|---|
| 店铺资料 | PATCH只发送变更字段，介绍空字符串清空 | 基于读到的店铺版本，不发送分类/审核信息；被拒重提是另一完整请求 |
| 营业时间 | **整周完整替换**，未列星期休息 | 每天最多4段；全部移除后保存才清空。相邻合并、重叠拒绝；已有排班/预约须被新时间覆盖 |
| 服务目录 | 新建或修改选中服务、上下架 | 元输入严格转换为整数分；理发15～240分钟且15倍数；打印时长显式null、价格仅参考起价。新建默认下架，可显式上架 |
| 打印价目 | **只保存勾选规格，未勾选保留** | A4四种规格；新规格显式null版本，已有规格带各自版本。要停用需勾选该项并关闭启用；不是取消“本次保存”。任一失败整批回滚 |
| 人员资料 | “保存姓名与启停” | 与绑定/排班共用人员版本；人员不创建登录账号，启用不保证可预约 |
| 服务绑定 | “保存完整服务绑定”，不是增量 | 0～50个本店理发服务，可绑定下架服务；空集合解除全部。资料和绑定是两个明确动作，不承诺跨两个请求原子保存 |
| 当日排班 | **所读取人员/日期的完整替换** | 0～4段，15分钟对齐，须在营业区间；空集合清空。今天至第6天可写，其余日期可读不可写；采用GET返回的人员版本 |
| 管理员审核 | 原读取版本＋批准/拒绝原因 | 旧版本或已被处理时不自动换版本重试，不提供暂停/恢复或审核历史列表的伪入口 |

价格输入支持0.01～1000.00元，接口始终发整数分；不接受指数、负数或小数分。ID/version保持字符串，不因浏览器大整数精度改变。营业时间和排班输入是上海本地HH:mm，不按浏览器纽约时区转换。

切换打印服务或排班人员/日期后，必须先“读取”对应资源才能保存；保存使用冻结的读取目标和版本，避免旧表单写到新目标。旧版本/状态冲突或网络结果不确定时，保留当前草稿、显示错误code/traceId并阻止直接重复提交，用户明确重新读取核对后才恢复。**重新载入（覆盖草稿）**本身是明确的放弃修改动作；页面不会拿最新版本偷偷重发旧修改。

服务、人员和申请的新建接口本身不是幂等创建。页面只防止当前页面中的重复提交及结果不确定后的直接重试，不保证刷新/关页后的重复创建被后端去重。应先登录/重新读取列表核对；不能把订单已有的创建幂等推广为所有新增接口都有幂等键。

有未保存修改时，路由、页签或编辑目标切换使用页面内“保留草稿 / 丢弃草稿并继续”，实现参考[Element Plus Dialog](https://element-plus.org/en-US/component/dialog.html)。不会调用浏览器原生confirm；切换账号会取消未完成的选择。浏览器硬刷新/关闭标签页不保存草稿，密码不会写入草稿或日志。

## 复现验收

- 正常项目库：使用自己的商家/管理员账号，按上面点击流程操作；不要把报告中的临时账号当正式库账号。
- 自动边界：运行`scripts/frontend.ps1 -Action Test`，当前3类/57项，包括31项原有及26项新增经营表单/异步/草稿选择检查。
- 构建：运行`scripts/frontend.ps1 -Action Build`，完成类型检查与静态打包；后端Maven打包方式不变。
- 隔离浏览器环境：使用[前端指南](frontend.md)的`preview-frontend.ps1 -Action Start/Status/Stop`，创建自己的两类商家，使用夹具提供的虚构管理员审核。它验证空库/独立datadir再写入，缓存关闭；不是原项目库数据迁移。

重点检查拒绝→重提→批准、两个管理员读同版本后的冲突、价目遗漏保留/停用、下架服务绑定、空集合解绑、日期切换禁存、排班清空与历史只读，以及缩短营业时间被已有排班拒绝。版本/保护冲突应保留当前草稿，重载显示原数据库事实，不能出现“失败但界面当作保存成功”。

当前没有学生打印下单/订单页或商家履约任务页；预约候选/创建及管理异常等继续按C、D批接入。业务保护仍依赖后端真实MySQL事务和锁；前端的按钮与草稿提示不代替权限、事务或并发保证。
