# 商家经营资料与营业开关：已确认规则

- 日期：2026-10-19（Asia/Shanghai）。
- 状态：用户回复“采用并实现”，已确认本方案；实施取舍见 [ADR-0013](decisions/0013-merchant-operation.md)，实际验证见 [经营验收](merchant-operation.md)。
- 来源：商家重提交付后，用户要求“进行下一项”；本项先落实此前推荐的经营规则定稿。
- 推荐范围：只实现一个已规划接口 PATCH /api/v1/merchant/shop，复用现有六张表、店铺版本和登录会话。

## 1. 已确认的基础

ADR-0010 已确认：批准商家后默认停业，商家随后主动开启营业；APPROVED 店铺可公开展示，能否接单还受营业时间与服务等条件影响。账号、成员、店铺各有不同状态，不以 JWT 中的历史信息代替数据库当前状态。

申请、审核、重提已实现。营业时间、服务配置、公开商家查询、订单及平台暂停操作尚未实现；完整接口规划中出现这些内容不等于规则已全部批准。

## 2. 已采用的业务行为

| 项目 | 推荐方案 | 理由与影响 |
|---|---|---|
| 谁能操作 | 当前账号 ACTIVE / MERCHANT，且本人 OWNER 为 ACTIVE、店铺 APPROVED | 未审核、被拒、被暂停的店铺不能绕过经营门槛；本人申请信息仍可查询 |
| 可修改资料 | name、locationText、description；修改后直接生效，不重新进入审核 | V1 审核经营资格，基础展示资料按日常维护处理；保留原审核记录，不据此宣称管理员审核过新文本 |
| 不可自助修改 | 分类、校区、归属、审核信息及角色；请求包含这些字段时拒绝 | 本次维持已审核的分类与归属边界；跨分类变更以后单独讨论 |
| 营业开关 | businessEnabled 为真正的 JSON 布尔值，可由符合条件的商家主动设为 true / false | 批准不自动开启；停业后仍允许修改资料，再次开启也需重新检查权限与状态 |
| 开启前置条件 | 本项允许符合经营资格的商家先开启开关，不要求尚未开发的营业时间或服务配置 | 开关仅保存商家意愿；后续接单必须同时检查营业时段、服务与场景条件，不把 true 当作可以下单的充分条件 |
| 停业影响 | 只影响后续接单资格，不撤销审核资格、不注销账号、不删除资料 | 沿用已确认基线：临时停业不能自动取消或阻止存量订单履约；订单模块实现时补充真实验证，本项不声称订单能力已完成 |

如果希望“配置好营业时间和服务后才能开启”，需要先开发这些能力，并明确理发/打印各自的开店条件。本提案推荐先保存独立开关，使本任务可以单独实现和验收；未来新增开店门槛时仍须讨论，不能静默改变行为。

## 3. 已确认的接口与输入规则

PATCH /api/v1/merchant/shop，成功 200 / OK，data 使用现有 MerchantShopView。身份与店铺从会话及成员关系取得，不接收客户端 shopId。

```json
{
  "expectedVersion": "5",
  "name": "星海模拟理发店",
  "locationText": "虚构校区服务中心 102",
  "description": "用于学习验收的店铺介绍",
  "businessEnabled": true
}
```

版本示例以 GET /merchant/shop 的实际返回为准，不使用 GET /me 的账号版本。字段为 name，与查询响应及原经营草案一致；首次申请和重提的 shopName 不作为本接口别名。

- expectedVersion 必传，使用规范的非负十进制字符串，范围与现有店铺版本相同；拒绝数字、null、空白、前导零与溢出。
- 四个可变字段均可省略，未传表示保留原值。只传 expectedVersion 时按现有昵称接口惯例，检查权限、状态和版本后返回当前资料。
- name、locationText、description 严格要求 JSON 字符串，拒绝 null、数字、布尔值、数组和对象；未知字段一律拒绝。
- 名称、位置、介绍去首尾空白后分别为 1～80、1～200、0～1000 Unicode 码点，拒绝非法 Unicode。清空介绍传空字符串或空白字符串；此 PATCH 的省略语义不同于完整重提的清空语义。
- businessEnabled 严格要求 JSON true / false；不接受字符串 "true"、数字 0/1 或 null。
- 规范化后确有变更时 shop.version + 1，多字段修改也只加一次；值相同或未传可变字段不增加版本。即使没有实际变更，也必须检查版本，旧版本仍返回 409。
- 版本达到 BIGINT 上限时，实际变更返回 409；无变更且版本匹配仍可返回当前资料，沿用昵称修改行为。

建议错误沿用现有契约：未登录/失效会话 401；非商家 403 / ROLE_FORBIDDEN；账号停用 403 / ACCOUNT_DISABLED；店铺未通过审核（含 SUSPENDED）403 / SHOP_NOT_APPROVED；本人 OWNER 非 ACTIVE 403 / ROLE_FORBIDDEN；无归属店铺 404 / RESOURCE_NOT_FOUND；版本冲突 409 / CONFIG_VERSION_CONFLICT；输入错误 400 / VALIDATION_FAILED。未通过资格检查不允许用无变更请求绕过权限。

## 4. 实现与事务取舍

不新增依赖、缓存、消息队列或数据库表，沿用 merchant 模块内分层、MyBatis-Plus 和注解 SQL。固定白名单更新字段，避免把整份实体直接绑定为可写请求。

锁顺序沿用账号资料与审核流程：本人账号 → 当前会话 → 店铺 → 本人 OWNER。查归属时不先锁成员；持有店铺锁后再次按账号限定 OWNER。锁内复查账号、角色、会话、归属、店铺/成员状态与店铺版本，真正写入前再次检查会话到期。由于本项不允许修改分类，无需新增分类锁。

同一事务提交所有变更与一次版本递增，任何失败整体回滚。不修改账号版本、不撤销登录会话、不追加新的审核记录，也不清空既有审核信息。未来营业时间同样使用 shop.version；当前按已有版本机制处理冲突，不自动重试覆盖。

## 5. 完成标准与后续

本轮实现一个 PATCH 接口，运行接口由 15 增至 16，规划总数保持 62；运行快照及完整规划随实际导出同步。

人工验收优先 Swagger / Apifox：管理员批准 → 商家登录 → GET 本人店铺 → 修改资料并开启 → GET 确认 → 关闭 → 用旧版本修改应冲突。验证修改不重新审核、默认停业保持到本人开启，原审核记录不被改写。

验收要求：独立真实 MySQL 覆盖权限与归属、PENDING/REJECTED/SUSPENDED、成员非 ACTIVE、账号/会话失效、严格类型及 Unicode 边界、多字段原子提交、无变更版本语义、并发修改、写后异常回滚与版本上限；同步注解、运行快照、完整规划和点击验收指南。具体执行结果以 [验证记录](merchant-operation.md) 为准，不将本要求当作测试结果。

本项交付后建议再定稿营业时间；随后推进服务配置与公开商家查询。平台暂停/恢复、分类变更及订单规则不在本项顺带实现。
