## 1. 已采用规则与取舍

| 项目 | 已采用方案 | 理由与影响 |
|---|---|---|
| 身份 | 理发师是店铺人员资料，不是平台登录账号 | 不创建用户名、密码或新角色，由本人商家统一维护 |
| 权限 | ACTIVE / MERCHANT + 本人 ACTIVE OWNER + APPROVED 店铺，且分类为 HAIRCUT | 沿用经营权限；PRINT 商家不支持这四个接口，返回 400 / VALIDATION_FAILED |
| 经营准备 | 店铺停业、未配置营业时间、理发师停用时，仍可维护人员和绑定 | 配置启用不等于已具备可预约时段，不自动开启店铺或生成排班 |
| 姓名 | displayName 去首尾空白后 1～40 Unicode 码点，拒绝非法 Unicode；允许重名 | 沿用已有字段长度；按 ID 区分人员，不增加姓名唯一约束 |
| 新增 | 必传 displayName 和 serviceIds，默认 enabled=false、version="0" | 先准备资料再通过 PATCH 启用；新增请求不接受 enabled 或其他额外字段 |
| 绑定 | 每位理发师可绑定 0～50 个不同的本店 HAIRCUT 服务 | 明确请求规模上限；允许空数组先建人员、以后补服务；同一服务可由多名理发师提供 |
| 服务上下架 | 可以绑定本店下架的理发服务；服务下架时不自动解除关系 | 支持提前准备、后续重新上架；未来可预约检查仍须同时满足服务和人员启用等条件 |
| 启停与删除 | 通过 PATCH 启停，无物理删除、无跨店转移 | 保留人员身份和未来历史引用；停用不自动清空绑定，也不自动取消订单 |
| 版本 | 姓名、启停和绑定共用 barber.version；不递增店铺或服务版本 | 同一人员两个页面的过期编辑会冲突，不同人员使用独立版本 |
| 同内容 | 规范化后没有实际变化时不写入、不递增版本，但仍校验权限及版本 | 绑定数组仅改变顺序不算变化；旧版本仍然返回 409 |

本轮不要求启用前必须绑定服务，enabled 仅表示人员启用意愿。允许“已启用但无绑定服务”的准备状态，未来没有匹配服务或有效排班时不会因此可预约。这个选择与店铺开关、服务上架的已有准备方式一致。

serviceIds 必须是 JSON 数组，元素为规范正十进制 BIGINT 字符串，不接受数字、null、空白、前导零、越界值；重复 ID 返回 400，不静默去重。空数组允许，字段省略或 null 拒绝。最多 50 项是本轮确认的单人绑定上限，不是全店服务总数或理发师人数上限。

所有绑定都必须属于本人店铺且为 HAIRCUT：非法 ID 格式为 400，不存在或他店服务统一 404，不返回对方名称等信息；本店非 HAIRCUT 服务为 400。任一项不合法，整个新增或绑定请求失败，不留下部分人员或关系。

分类字典停用仍只限制新入驻/重提选择，不自动停用已批准的 HAIRCUT 店铺。四个接口先检查本人经营资格与分类；通过这些检查后，不存在或非本店理发师统一 404。客户端不能指定或修改 shopId、accountId、role、version 等服务端字段。

## 2. 四个接口

| 方法 | 路径（统一以 /api/v1 开头） | 结果 |
|---|---|---|
| GET | /merchant/barbers | 本店理发师数组，包含启用和停用人员及 serviceIds |
| POST | /merchant/barbers | 同事务创建人员和初始服务关系，201 / OK，返回完整人员视图 |
| PATCH | /merchant/barbers/{barberId} | 部分修改 displayName / enabled，200 / OK，返回完整人员视图 |
| PUT | /merchant/barbers/{barberId}/services | 完整替换此人的服务集合，200 / OK，返回完整人员视图 |

返回 MerchantBarberView：id、displayName、enabled、serviceIds、version。id / version / serviceIds 元素均为字符串，serviceIds 按数值 ID 升序返回，包括尚未上架的已绑定服务。

GET 无筛选、无分页，固定 created_at DESC、id DESC；没有人员返回 []。这是商家维护列表，不是匿名理发师查询或可预约查询。不新增详情、删除、排班或学生端接口。

### 新增

```json
{
  "displayName": "模拟理发师小林",
  "serviceIds": ["201", "202"]
}
```

示例 ID 必须替换为本店实际 HAIRCUT 服务 ID；也可显式传 []。返回 201，enabled=false、version="0"。姓名允许重复，POST 不提供创建幂等回放；相同请求重复发送会创建不同人员 ID，不承诺自动去重。

### 修改姓名或启停

```json
{
  "displayName": "模拟理发师林老师",
  "enabled": true,
  "expectedVersion": "0"
}
```

expectedVersion 必须提供，从本人的理发师查询结果取得，不是店铺或服务版本。displayName / enabled 省略时保持原值，显式 null 拒绝；enabled 仅接受 JSON 布尔值。PATCH 不接受 serviceIds，服务关系统一通过 PUT 维护。

姓名、enabled 任一实际变化，只递增一次 barber.version；只传当前 expectedVersion 或相同内容是无变化请求。BIGINT 版本达到上限时只允许无变化，实际修改返回 409 / CONFIG_VERSION_CONFLICT。

### 完整替换绑定集合

```json
{
  "serviceIds": ["201"],
  "expectedVersion": "1"
}
```

如果原来绑定 201、202，此请求保留 201 并解除 202；serviceIds=[] 表示清空所有关系。与打印价目的“遗漏规格保留”不同，这里传的是此人的完整目标集合，不能只提交想新增的一个 ID。

PUT 与 PATCH 共用理发师版本。只有集合真正改变才递增一次版本；相同集合即使输入顺序不同也不递增，重复 ID 仍拒绝。先检查权限、版本和所有目标服务，再以一个事务增删关系；任一步失败整体回滚。人员姓名和 enabled 保持原值，不修改服务内容或价格。

## 3. 错误与尚未实现的预约边界

认证无效 401；账号/角色/店铺/OWNER 不满足既有经营资格时沿用现有 403；分类不支持、字段/类型/长度/数组格式错误为 400 / VALIDATION_FAILED；通过经营资格与分类检查后，不可见理发师或服务为 404 / RESOURCE_NOT_FOUND；旧版本或版本上限下实际变更为 409 / CONFIG_VERSION_CONFLICT。内部故障沿用统一 500，不返回 SQL 细节。

当前没有排班或预约表，人员停用、解除服务关系只改变配置，不声称已经检查或处理存量预约。保留原有讨论稿中“有效预约须先处理，不能直接取消存量订单”的方向；预约模块接入前，必须为停用、解绑及其他影响预约的配置修改补齐冲突检查、日期保护行锁顺序和真实 MySQL 验收。有效预约的精确状态/时间范围届时定稿。

不能把当前数据库没有预约记录当作已经支持预约安全停用，也不能在有订单功能后继续无条件套用本轮配置逻辑。未来订单冻结服务、价格和人员名称快照，姓名或服务价格变更不得重写已有订单内容。

## 4. 数据与事务方案

V7 新增 barber、barber_service，不改写 V1～V6，不增加框架或基础设施。继续使用 merchant 模块内的 Controller / Service / DTO / VO / Entity / Mapper，SQL 沿用 MyBatis-Plus 与注解。

- barber：id、shop_id 外键、display_name VARCHAR(40)、enabled、version、created_at、updated_at；店铺归属创建后不可改，索引 (shop_id, enabled, id)，CHECK 兜底非空姓名、布尔值与非负版本。
- barber_service：id、barber_id 外键、service_id 外键；(barber_id, service_id) 唯一，另建 service_id 索引，外键限制悬空引用及误删。沿用原逻辑设计，不重复存 shop_id。

两个独立外键只能保证资源存在，不能保证同店或服务类型。应用在锁内验证同店 HAIRCUT；不把外键描述为已经完成跨店隔离。

配置写锁顺序为本人账号 → 当前会话 → 店铺 → 本人 OWNER → 本次目标服务（ID 升序）→ 理发师 → 关系。PATCH 不修改服务关系，可跳过目标服务锁；新增人员在校验服务后写入，PUT 在读取当前关系并核对版本后仅增删差异项。所有相关事务保持一致的锁顺序；店铺锁继续协调同店经营写入，不承诺不同人员的物理写入并行。

写事务采用 READ COMMITTED，父店铺/理发师协调新增与关系变更，锁后使用当前读核对权限、版本及当前服务集合；在写入前后复查会话有效期，异常整体回滚。查询使用只读 RR，一致快照读取人员和绑定；批量加载关系，避免每个理发师再单独查询。

这套顺序只覆盖本轮配置。后续排班/预约需要先协调“理发师 + 日期”保护行，不能在持有配置锁时反向获取日期锁，届时必须同步调整受影响的配置路径并验证。
