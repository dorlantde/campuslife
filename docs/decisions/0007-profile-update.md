# ADR-0007：本人昵称修改与版本冲突

- 日期：2026-10-15（Asia/Shanghai）
- 状态：用户授权推进此前推荐的昵称与版本任务；实现与独立 MySQL 验证通过
- 范围：PATCH /api/v1/me，只更新本人 nickname，复用 account.version

昵称沿用已确认的注册规则，不新增敏感词、实名或修改次数规则。请求仅接受 nickname 与 expectedVersion，身份来自服务端会话。PATCH 保留“遗漏不修改、null 拒绝”的语义；归一化后无变化不增加版本，但仍检查传入版本。

expectedVersion 为规范的非负 BIGINT 十进制字符串，拒绝 JSON 数字与隐式转换，避免 JavaScript Number 丢失精度。使用 JsonNode 接收两个字段，以区分未传、显式 null 与非字符串值，再由服务校验；没有改变其他接口的 JSON 转换配置。成功返回最新 AccountView，实际变更时 version + 1；版本过期或无法递增返回 409 / CONFIG_VERSION_CONFLICT。客户端重新读取并让用户决定是否继续，不能自动重试覆盖。

事务内先锁账号再锁当前会话，复用登录与改密的账号锁顺序，重新检查当前身份状态；再核对版本，用带 id、version、ACTIVE 条件的 SQL 修改昵称与版本，并检查影响行数。这样版本保护旧页面，锁与事务保护与其他账号写操作的协调及一致响应。代价是同账号短事务串行，当前学习项目优先可解释的正确性，不提前引入乐观锁插件或其他基础设施。

修改昵称不会撤销会话，不影响其他账号、摘要或角色。改密会递增同一个账号版本，旧资料页面需要重新读取。沿用当前数据库结构，没有修改已执行的 Flyway V1。

本机步骤、自动测试范围与实际执行记录见 [昵称修改验收](../profile-update.md)。商家申请与审核规则仍为后续待定业务，不因本次个人资料任务视为已批准。
