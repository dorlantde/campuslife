# ADR-0018：理发师按日排班与营业时间保护

- 日期：2026-10-21（Asia/Shanghai）。
- 状态：用户已选择“采用并实现”；实现范围为两个排班接口、V8 迁移和营业时间保护。验证记录见[验收指南](../merchant-schedule.md)。
- 依据：[已确认提案](../merchant-schedule-design.md)、[ADR-0014](0014-merchant-business-hours.md)、[ADR-0017](0017-merchant-barbers.md)。

## 决定

GET /merchant/barbers/{barberId}/schedule 必传严格 YYYY-MM-DD 的 date，允许读取 1000～9999 年真实日期；PUT 必传 date、expectedBarberVersion、intervals，只能写校园时区今天至第 6 天。店铺须 APPROVED / HAIRCUT，账号及本人 OWNER 须 ACTIVE；停业、人员停用或没有服务绑定仍可准备排班。

原始最多 4 段、严格 HH:mm、起止均为 15 分钟倍数；开始早于结束、不跨午夜。排序、相邻合并，重叠/重复拒绝，每段须完整位于该星期的一段营业时间内。营业时间仍为原有分钟精度。完整替换一人一天，[] 清空，其他日期/人员不变；今天的完整计划允许包含已过去时段。

沿用 barber.version 和 expectedBarberVersion，与姓名/启停、绑定及其他日期共用。实际变化加一，无变化不写入但仍验证版本、权限与窗口；上限只允许无变化。这会使不同日期的页面也可能发生版本冲突，V1 接受这一简单取舍。响应为 date、intervals、barberVersion；时段统一 startTime/endTime，纠正规划生成器此前错误的 startAt/endAt。

V8 增加 barber_day_guard 与 barber_schedule；日期为校园本地 DATE，起止换算为 UTC DATETIME(3)。保护行有人员外键及人员/日期唯一键，时段通过复合外键关联保护行。首次非空保存创建保护行，清空保留；GET 和未配置日期的空保存不创建。保护行、时段替换、版本增加同一事务，任何失败回滚。

营业时间实际变更须覆盖本店今天及之后全部已保存排班，包含停用人员，今天按完整日期保护；否则 409 SCHEDULE_CONFLICT。不自动裁剪，先调整/清空排班再修改营业时间。历史日期不阻止修改。成功只增加 shop.version。排班使用锁后的最新营业时间，范围失效为 400 VALIDATION_FAILED。

## 明确替代旧锁顺序

早期预约草案及 ADR-0017 提出的“日期保护行在店铺配置之前”与已实现配置的店铺入口不一致，混用会形成相反取锁顺序。此次经用户确认，**店铺作为统一前置协调行，再获取日期保护行和人员/时段资源**。旧顺序被本记录替代。

- 配置使用 shop FOR UPDATE；当前排班写顺序为账号 → 会话 → 店铺 X → OWNER → 日期保护行 → 人员/时段，RC 隔离，等待后复查会话、日期及版本。
- 营业时间在店铺 X 内枚举今天及之后的保护行，按 (barber_id, service_date) 升序锁定，检查后才更新营业时段。店铺入口阻止枚举期间并发新建日期。
- 未来预约等交易先获取店铺 FOR SHARE，再获取日期保护行 FOR UPDATE，之后配置/订单；多日期按相同顺序。不得持日期锁后再反向申请店铺锁。相关交易尚未实现，届时所有影响占用的路径须统一验收。
- GET 使用只读 RR，人员版本与时段来自同一快照。PUT 在锁等待后及实际写入后、返回前复查 Clock 的日期窗口和会话，过午夜或过期整体回滚。

此方案不引入 Redis/新锁服务，代价是同店配置写会阻塞该店相关交易；正确性优先，未声称任何性能提升。已有服务/人员配置继续由店铺 X 协调，停用和解绑不自动删除排班；有效预约保护将在订单接入前补齐。

## 交付边界

不实现预约订单、占用、可约查询或提前 2 小时筛选，不把排班等同于可接单。权限、严格输入、UTC 往返、共享版本、SQL 后异常回滚及真实 MySQL 锁等待由集成测试验证。人工验收与实际执行结果见[排班指南](../merchant-schedule.md)。
