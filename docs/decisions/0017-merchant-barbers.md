# ADR-0017：理发师管理与服务绑定

- 日期：2026-10-21（Asia/Shanghai）。
- 状态：用户对 [理发师提案](../merchant-barbers-design.md) 明确选择“采用并实现”；本记录说明最终实现取舍。
- 范围：本店理发师 GET / POST、PATCH /{barberId}、PUT /{barberId}/services 及 V7 两表迁移。不包含排班、匿名查询和预约。

理发师是店铺人员资料，不创建登录账号或新角色。权限沿用 ACTIVE / MERCHANT、本人 ACTIVE OWNER、APPROVED 店铺，并要求 HAIRCUT 分类；PRINT 商家访问这些接口为 400。店铺停业、没有营业时间、人员停用仍可维护资料和绑定。

姓名去首尾空白后 1～40 Unicode 码点，拒绝非法 Unicode，允许重名。创建必传姓名和 serviceIds，默认停用、version="0"，不接受 enabled 或服务端归属字段。POST 不提供创建幂等回放，重复提交可创建不同人员。

每人可绑定 0～50 个不同的本店 HAIRCUT 服务，含下架服务；服务 ID 必须为规范正十进制 BIGINT 字符串，重复 ID 拒绝。可以先建空绑定人员，也允许启用空绑定人员；启用不等于可预约。同一服务允许绑定多名理发师，服务下架不自动解绑。

PATCH 仅支持姓名、启停和必传理发师版本；省略保留、null 拒绝。PUT 必传完整 serviceIds 和理发师版本，空数组清空关系，遗漏服务被解绑。两者共用 barber.version，实际变化才递增一次，集合顺序不构成变化；无变化仍核对权限和版本，版本上限只允许无变化。不递增店铺或服务版本，不修改价格，无物理删除或跨店转移。

V7 新建 barber、barber_service，包含店铺/人员/服务外键、关系唯一键和姓名/布尔/版本 CHECK。不重复存关系的 shop_id；两个独立外键不保证同店 HAIRCUT，应用须在锁内验证。实体插入用 MyBatis-Plus，其他专用 SQL 沿用注解方式，不增加依赖或 XML。

写事务为 READ COMMITTED，顺序为本人账号 → 当前会话 → 店铺 → 本人 OWNER → 本次目标服务（ID 升序）→ 理发师 → 关系。PATCH 可跳过服务锁；PUT 使用当前读核对人员和完整关系，仅增删差异项，保留未变关系身份。会话在锁后及写入前后复核，任何异常整体回滚。店铺锁协调同店写入，不承诺不同人员的物理写入并行。

GET 使用只读 RR，一致快照读取人员与关系；人员按创建时间/ID 倒序，绑定 ID 数值升序。单次批量加载本店关系，避免逐人查询；返回启用与停用人员，不含账号或会话数据。

本轮没有预约表，停用和解绑只完成配置变更，不声称已支持预约存量保护。预约接入前须按日期保护行协议补齐冲突检查并调整受影响的配置路径，不得在配置锁后反向取得日期锁。实际验证及点击流程见 [理发师验收](../merchant-barbers.md)。

2026-10-21 后续变更：用户确认 [ADR-0018](0018-merchant-schedule.md)，按日排班已实现并共用人员版本。上文关于日期行与配置的旧顺序被明确替代为店铺入口（配置 X / 未来预约 S）→ 日期保护行 → 人员/时段等后续资源；不得再沿用日期行先于店铺的相反顺序。停用/解绑不自动删除排班，有效预约保护仍须在订单接入前完成。
