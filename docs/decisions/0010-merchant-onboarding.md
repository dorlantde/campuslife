# ADR-0010：商家入驻与审核

- 日期：2026-10-19（Asia/Shanghai）。
- 状态：用户明确确认全部推荐提案，并授权开发。
- 确认来源：用户“你的提案通过，进行开发”。完整规则见 [入驻方案](../merchant-onboarding-design.md)。

## 决策

1. 独立商家申请入口同事务创建 ACTIVE / MERCHANT 账号、PENDING 店铺和 PENDING OWNER；不自动登录，不改变已有学生角色。账号规则沿用认证模块，所有角色共享用户名唯一索引。
2. 基础分类通过迁移初始化理发、打印；不绑定本轮尚未实现的服务类型限制。不收集真实身份证件、手机号和营业执照；校区固定 XINGHAI_MAIN。
3. 待审、被拒商家可以登录、管理自己的账号资料并查看审核信息，不能经营。读取店铺始终按当前会话的账号归属，不使用客户端传入的 shopId。
4. 被拒允许修改资料重新提交，复用原账号、店铺，REJECTED → PENDING。待审不能修改或撤回。保留历次审核人、结果、原因、时间及被审核版本。
5. ADMIN 仅审核 PENDING；批准激活成员，拒绝必须填写原因。审核及重提必须校验版本，同一版本并发只有一个成功，其他请求 409。
6. 审核通过后仍默认停业，商家配置经营资料后主动营业；APPROVED 店铺公开可见，是否接单另受营业、时间及服务条件限制。
7. 首位业务管理员通过显式本机初始化命令受控创建，不提供公开注册或默认密码，不覆盖已有账号或自动提权。

## 当前实现边界

第一项交付只实现分类、提交申请和读取本人待审店铺。审批、管理员初始化、重提和审核历史存储按后续小任务实现，不能把本决策通过解释为它们已可调用。

第二项落实管理员初始化、列表/详情/批准/拒绝及 V3 审核历史，见 [ADR-0011](0011-admin-shop-review.md)。第三项完成被拒后修改重提，见 [ADR-0012](0012-merchant-resubmission.md)，复用现有表，无新增迁移；此段更新当前状态，不改变原确认规则。

新增 V2 迁移建立 shop_category / shop / shop_member，V1 不修改。当前 V1 只有一个 OWNER，shop_member 的 account_id、shop_id 分别唯一；以后扩展多成员时再迁移，不提前支持 STAFF。审核历史表在审批任务中建立，避免尚未使用的结构。

申请的 BCrypt 在事务外计算，事务内按“分类共享锁 → 插入账号 → 插入店铺 → 插入成员”执行。共享锁保证分类在申请提交前不会被并发停用；唯一索引裁决重复用户名。任一插入失败必须回滚三者，异常在事务退出后转换为统一 HTTP 错误。

没有新增基础设施或依赖，保留 MyBatis-Plus、注解 SQL、模块内分层及本机启动配置。

## 验收

Swagger 按“分类 → 申请 → 登录 → Authorize → 本人店铺”执行，见 [入驻验收](../merchant-onboarding.md)。数据库约束、并发重复、回滚、角色与归属边界使用独立真实 MySQL 验证。实际执行记录随该指南维护，不将设计稿当作测试结果。
