## 选择与取舍

- 一个Java应用实例，Compose默认基础模式3服务，显式技术演示模式7服务；保留已有事务、互斥、幂等和维护协议，不声称支持多实例或HA。
- 新部署选择MySQL8.4 LTS，先固定实际可用补丁和digest并验证原迁移、约束、关键查询及代表性真实并发。当前电脑MySQL8.0、数据和VS Code配置保持；不原地升级，不重写历史迁移或放宽约束来制造兼容。
- 原私有S3采用原生TLS/CA与服务名校验，不扩大跨容器明文许可。秘密文件、独立组件身份、显式无HTTP维护CLI；镜像不包含本机秘密或测试类。
- 最小Actuator/Micrometer独立私有管理面，采用与业务身份独立的运维认证；先验证权限、故障诊断和基本指标，不先增加Prometheus/Grafana。
- 全栈恢复覆盖数据库、RabbitMQ、券Redis、S3、LOCAL根和配置身份；沿原暂停/排空/代次恢复协议，验证恢复后新写，不用容器重启代替恢复证据。

## D.3 小内存演示配置

2026-11-04，用户明确代金券仅支持2核4 GiB，并在说明这是同项目的部署配置后授权实施。采用[compact4g](../compact4g-deployment.md)：只供新showcase实例显式选择，保留同一业务JAR、七服务和原业务协议；常驻内存上限合计3 GiB，同用逻辑CPU 0、1，容器不使用Swap。Java堆448 MiB/池与线程有界，MySQL缓冲池128 MiB/40连接且保留原提交持久性，Rabbit告警384 MiB/容器640 MiB。默认standard/已有实例不变，不接受静默原地改profile。

该方向不要求8 GiB采购。先进行有界本地预验证，再核对新ECS并实机验收；CPU隔离和逐容器限额不能冒充完整4 GiB宿主、容量或稳定性保证。构建先于业务启动，维护客户端串行且额外占用内存；本项不扩展E冷备验证，compact4g在E冻结/备份入口明确拒绝。用户原ECS的SSH仍在握手阶段关闭，尚未操作服务器；前端暂停。
