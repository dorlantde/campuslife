# 管理员预约异常核实与退款关闭：已确认方案

- 日期：2026-10-22（Asia/Shanghai）。
- 状态：用户已明确“采用并实现”；决策见[ADR-0027](decisions/0027-admin-booking-exception.md)，交付与实际验证见[验收指南](admin-booking-exception.md)。
- 依据：[业务基线](decisions/0001-v1-baseline.md)、[接口契约](v1-api-contract.md)、[状态与事务](v1-state-transitions.md)、[模拟资金 ADR-0023](decisions/0023-booking-mock-payment.md)、[履约 ADR-0026](decisions/0026-booking-fulfillment.md)。

已确认的基线是：预约结束仍未到店、服务开始后发生异常，均由管理员核实后全额模拟退款并关闭；记录操作人和原因，不自动认定责任，不部分退款。本方案细化管理员权限、可处理状态、版本与重复请求、占用及并发规则。

## 1. 本轮范围

| 接口 | 建议行为 |
|---|---|
| GET /api/v1/admin/orders/{orderId} | 管理员查看任意店铺的 BOOKING 详情，包括现有时间、状态、版本、支付/退款及关闭原因 |
| POST /api/v1/admin/orders/{orderId}/close-exception | 核实后填写原因及读取时的订单版本，全额模拟退款并关闭 |

均返回现有 OrderDetail；只实现 BOOKING，非预约或不存在统一404 RESOURCE_NOT_FOUND。详情可查看任意预约状态，查询不自动关闭或退款。不新增学生联系方式、密码、文件链接或独立事件列表。

实现后运行接口43→45，完整规划仍62，待开发19→17。沿用 order 模块、V9/V10订单/资金/事件模型和现有19张业务表，预计无需迁移、XML、新依赖或基础设施。

本轮补齐正常履约以外的人工异常出口；不包含投诉提交、证据上传、多级审批、部分退款、已完成订单售后、打印异常、订单列表或管理员手工改状态。V1的“核实”由管理员实际了解情况后提交文字结论，不宣称系统自动证明到店或责任。

## 2. 权限、状态与时间

仅 ACTIVE / ADMIN 账号及有效会话可读、可写；学生和商家403 ROLE_FORBIDDEN，管理员账号停用403 ACCOUNT_DISABLED，会话失效沿用401。管理员仍通过现有独立初始化入口创建，不增加公开管理员注册或默认密码。

建议处理旧单无需学生、商家账号或 OWNER 当前有效，也无需店铺仍获批准、营业或服务仍上架。否则账号停用后会失去异常处理出口。管理员只验证自己的权限，不反向加锁目标学生/经营账号，不受店铺归属限制。

首次关闭仅允许 **BOOKING + PAID + ACTIVE占用**，订单状态为 PENDING_ACCEPTANCE、ACCEPTED、IN_SERVICE 之一；成功支付金额必须与冻结 payableAmount 一致，且没有退款。待支付、已完成或已关闭均不生成新退款。

建议不设置学生提前1小时、商家预约开始前等普通取消窗口，也不要求ACCEPTED必须等到endAt。管理员可在核实无法履约后及时处理，亦可在预约结束仍未开始、或已经开始后的任意时刻处理；所有请求必须说明实际核实结论。时间使用锁后服务器UTC毫秒时刻，不能由客户端回填。

PENDING_ACCEPTANCE 继续保留原30分钟超时机制。若管理员与到期扫描竞争，谁先合法提交决定唯一关闭原因：管理员先提交记录 ADMIN_EXCEPTION；扫描先提交记录 ACCEPTANCE_TIMEOUT，管理员随后返回状态冲突。管理员入口本身不代跑超时关闭，不沿用商家接单的“先超时退款再返回409”；普通支付、接单及原扫描的期限行为保持现状。

## 3. 请求、版本与重试

管理员先读取详情，再提交：

```json
{
  "reason": "已向双方核实，预约结束后仍未到店，按V1规则全额模拟退款",
  "expectedVersion": "2"
}
```

orderId 为规范正BIGINT十进制字符串。reason 去首尾空白后1～300个Unicode码点；expectedVersion 为0～BIGINT最大值的规范十进制字符串。缺失、null、错误类型、空白、前导零版本、超长及未知字段均400 VALIDATION_FAILED。不接收金额、目标状态、操作人、客户端时间或额外 Idempotency-Key。

版本防止管理员核实期间订单发生变化：例如读取ACCEPTED版本2后商家已开始并变成版本3，提交旧版本2应409 CONFIG_VERSION_CONFLICT，重新查看并核实后才能处理。

锁后按以下顺序处理：

1. 验证管理员、会话、资源类型；权限不足不能重放成功结果。
2. 对 CLOSED 订单，仅当最后事件为 ADMIN_EXCEPTION、实际操作人为同一管理员、归一化原因相同、请求 expectedVersion 等于当前 version−1，且原退款和关闭/占用事实一致，才200返回原当前详情。其余关闭状态409 ORDER_STATE_CONFLICT。
3. 对非CLOSED订单，版本不匹配409 CONFIG_VERSION_CONFLICT；匹配但不是上述允许状态/支付/占用组合则409 ORDER_STATE_CONFLICT。COMPLETED不能退款。
4. 首次合法修改还须版本可递增及模拟资金开关开启；版本已达上限409 ORDER_STATE_CONFLICT，资金关闭503 MOCK_PAYMENT_DISABLED，均无写入。

重复成功不改时间、原因、版本、事件或退款；改原因、改管理员或改请求版本不能覆盖旧记录。已有合法结果的重放无需重新开启资金开关。先判断状态/版本再检查资金开关，避免无效请求被误报为资金关闭。

## 4. 原子结果、占用与审计

一次提交包含：唯一全额成功模拟退款；主单 CLOSED / REFUNDED、closeReason=ADMIN_EXCEPTION、closeNote为归一化原因、closedAt、version+1；一条 ADMIN_EXCEPTION 事件，记录实际 ADMIN 账号ID、原状态、目标CLOSED、核实原因及发生时间。退款 reason=ADMIN_EXCEPTION、reason_note保存同一原因。原成功支付、原金额、人员/服务快照及已发生的履约时间保持。

| 关闭前状态 | 关闭后预约占用 | 理由 |
|---|---|---|
| PENDING_ACCEPTANCE / ACCEPTED，未开始 | ACTIVE→RELEASED | 未使用时段提交后可以重新计算预约资格 |
| IN_SERVICE，已开始 | ACTIVE→CONSUMED | 保留整个原预约区间，不截短、不延长，避免退款后重复售卖已售时段 |

开始后CONSUMED沿用ADR-0022/0026：公开候选与创建继续排除原区间；未结束区间仍受排班/营业时间保护，人员启停/解绑沿用现有CONSUMED规则。开始前释放不保证过去或不足提前2小时的时段可再次下单，创建仍执行原时间规则。

复用订单事件作为核实审计，不新增独立工单表。接口只记录当前管理员提交的结论，不增加管理员修改历史原因或重开关闭订单的能力。事件列表查询继续留待后续任务。

## 5. 事务、验证与交付标准

写事务RC，锁顺序：当前管理员账号→当前会话→订单所属店铺S→日期保护行→订单/预约当前读→资金及事件。无需OWNER复核；不锁目标账号。锁等待后重新读取当前订单及版本，提交前复查管理员会话。读取详情使用只读RR一致快照。

与开始/完成、学生取消、商家拒单/取消、到期扫描及同日创建共享已有日期/订单锁。完成先提交则拒绝退款；异常关闭先提交则不能再开始或完成。两个管理员竞争、同管理员多端重试、扫描竞争最终只能留下一个关闭原因和一笔全额退款。退款、关闭、释放/消耗或事件任一步故障及提交前会话失效均整笔回滚；真实死锁/锁超时503 SERVICE_TEMPORARILY_UNAVAILABLE，不返回部分成功。

实现时须完成：

1. Swagger/Apifox点击指南：管理员登录并Authorize，使用已创建预约ID查看详情、复制version、填写核实原因、退款关闭；学生/商家详情同步展示结果。不提供绕过时间的调试接口。
2. 独立真实MySQL验证三种允许状态、未开始释放、开始后CONSUMED、未到店过期与已完成拒绝；模拟资金默认关闭、新退款受开关保护、成功重放不重复资金。
3. 覆盖管理员身份/停用/会话、目标账号和OWNER停用仍可处理、非法参数、版本上限/过期及同管理员/不同管理员重复请求。
4. 真实锁验证与开始/完成/到期扫描/普通取消及重叠创建竞争；较长预约开始后异常关闭，原未来区间仍不能再次售卖，原排班保护继续成立。
5. 真实数据库写入后注入退款、关闭、占用及事件失败，验证资金/主单/预约/事件原子性；不凭mock声称数据库锁成立。
6. 同步Swagger注解、运行及完整规划OpenAPI、重要决策记录与相关文档；按风险运行相关回归及可执行jar检查，记录实际执行结果，不访问现有项目服务数据。
