# 理发师按日排班：已确认方案

- 日期：2026-10-21（Asia/Shanghai）。
- 状态：用户已选择“采用并实现”；具体决定见 [ADR-0018](decisions/0018-merchant-schedule.md)，交付与验证见 [排班指南](merchant-schedule.md)。本文保留方案理由。
- 推荐范围：两个已规划的排班接口、V8 两张表，以及现有营业时间 PUT 对已排班时段的保护。预约、可约时段、订单另行推进。
- 基础：[营业时间 ADR-0014](decisions/0014-merchant-business-hours.md)、[理发师 ADR-0017](decisions/0017-merchant-barbers.md)、[接口契约](v1-api-contract.md)及[状态与锁协议](v1-state-transitions.md)。

## 1. 推荐业务规则

| 项目 | 推荐方案 | 理由与影响 |
|---|---|---|
| 权限 | ACTIVE / MERCHANT + 本人 ACTIVE OWNER + APPROVED 的 HAIRCUT 店铺 | 沿用理发师权限；PRINT 商家为 400，不可见人员在资格检查后统一 404 |
| 准备状态 | 店铺停业、理发师停用或尚未绑定服务时，仍可维护排班 | 允许提前准备；排班不自动启用人员、开启店铺或保证可预约 |
| 日期 | 按 Asia/Shanghai；GET 可读取合法历史日期，PUT 仅今天至第 6 天，含首尾共 7 个本地日期 | 给写入明确窗口，与 V1 的 7 天预约方向一致；排班窗口不等于已经实现预约开放规则 |
| 日期格式 | 必填严格 YYYY-MM-DD 的真实日期，数据库支持范围 1000～9999 年 | 不接受补零缺失、时区后缀、数字、null 或无效闰日；GET 日期仍须满足格式与数据库范围 |
| 时段 | startTime / endTime 为严格 HH:mm，均按 15 分钟对齐 | 与现有理发时长步长一致；不跨午夜、不接受 24:00，开始必须早于结束 |
| 分段 | 每人每天原始请求最多 4 段，排序后相邻合并，重叠或重复拒绝 | 支持午休；只改变顺序或等价拆分不算实际变化 |
| 营业范围 | 每段必须完整位于该星期的一个连续营业区间内 | 不得跨越午休；营业时间仍保持原有分钟精度，不自动取整 |
| 覆盖方式 | PUT 完整替换指定理发师的指定日期，intervals=[] 清空该日 | 不覆盖其他日期或其他人员；缺失/null 不表示清空 |
| 版本 | 沿用规划中的 expectedBarberVersion，使用 barber.version | 排班、姓名/启停和绑定共用人员版本，防止旧页面覆盖；不新增日期独立版本 |
| 同内容 | 规范化后无变化不写排班、不递增人员版本，但仍检查权限、日期窗口和版本 | 旧版本仍冲突；版本到 BIGINT 上限只允许无变化 |

共用人员版本的代价是：两个页面修改同一人的不同日期，也可能发生版本冲突；改姓名或绑定后也应刷新排班版本。V1 接受这项简单取舍，未来有实际需要再讨论日期独立版本，不能静默更换现有字段含义。

PUT 校验的是按日工作计划，不在排班端套用预约“提前 2 小时”的筛选，也不自动裁剪今天已经过去的时段。今天的完整计划可以保留上午时段；历史日期只读。未来可约查询和下单还须检查实时开始时间、服务时长、占用等条件。

如果该星期休息或未配置营业时间，只允许保存 []；非空计划为 400 / VALIDATION_FAILED。例：营业区间 09:00～12:00、14:00～18:00，排班 11:30～14:30 不合法，不能用当天最早开门至最晚关门作笼统覆盖。营业时间 09:10～17:40 时，可以排 09:15～17:30，但不能排 09:00～18:00。

## 2. 统一接口中的日期与时间

原接口契约约定排班使用日期和 HH:mm，但规划生成器的 ScheduleInterval 使用 startAt/endAt 瞬时时间，二者不一致。建议本次统一为 **date + startTime/endTime**，均按校园时区解释。请求与响应一致，数据库仍按项目约定保存 UTC DATETIME(3)，不能直接把本地时刻当成 UTC 入库。匿名可约查询将来使用 startAt/endAt，不与商家排班字段混用。

| 方法 | 路径（统一以 /api/v1 开头） | 结果 |
|---|---|---|
| GET | /merchant/barbers/{barberId}/schedule?date=YYYY-MM-DD | 200 / OK，指定日期的排班视图 |
| PUT | /merchant/barbers/{barberId}/schedule | 200 / OK，完整替换该日后的视图 |

GET 不创建保护行或排班。日期尚未配置时，返回该 date、intervals=[] 及当前 barberVersion；版本是整个人员的最新版本，不是该日的历史版本。时段按开始时间升序。

PUT 示例（日期及版本必须按实际查询替换）：

```json
{
  "date": "2026-10-22",
  "expectedBarberVersion": "2",
  "intervals": [
    {"startTime": "09:00", "endTime": "12:00"},
    {"startTime": "14:00", "endTime": "18:00"}
  ]
}
```

三个顶层字段及每个时段的两个字段必须提供；拒绝未知字段、null、非数组、null 时段以及错误类型。expectedBarberVersion 为规范非负 BIGINT 字符串，不是店铺、服务或账号版本。理发师 ID 沿用正十进制 BIGINT 字符串规则。

实际变化只递增一次 barber.version，不增加 shop.version 或 service_item.version，不改变人员姓名、启停及绑定。成功返回示例：

```json
{
  "date": "2026-10-22",
  "intervals": [
    {"startTime": "09:00", "endTime": "12:00"},
    {"startTime": "14:00", "endTime": "18:00"}
  ],
  "barberVersion": "3"
}
```

日期窗口在锁等待后按注入 Clock 与校园时区复核，避免请求等待至第二天后仍修改昨天；写入后再次检查会话和窗口，失败整体回滚。示例日期不代表长期可用测试数据。

## 3. 同步补齐营业时间与排班的一致性

仅在新增排班时检查营业时间不够：先排好 09:00～12:00，再把营业时间改为 10:00～11:00，会留下无效排班。建议本轮扩展现有 PUT /merchant/shop/business-hours：

1. 在同一写事务中读取本店今天及之后的全部已保存排班，包括停用人员的计划。
2. 新整周营业时间必须完整覆盖这些日期对应星期的每段排班；不覆盖则返回 **409 / SCHEDULE_CONFLICT**，营业时间、排班及各版本全部不变。
3. 不自动裁剪或清空任何人的排班。商家先按日修改/清空冲突排班，再重新保存营业时间。
4. 过去日期的排班不阻止修改每周计划；今天按完整日期保守保护，不按当前时刻忽略上午时段。
5. 营业时间成功变更仍只增加 shop.version，不增加人员版本；原有权限、相邻合并、无变化语义和严格字段规则保留。

排班保存使用锁后的最新营业时间，不新增 expectedShopVersion。若营业时间已变化而目标排班不再被覆盖，返回 400，提示重新查询营业时间并调整；不能因人员版本仍正确就绕过这项检查。没有实际变化的营业时间请求不改变既有数据，也不触发自动修复；当前没有预约表，不把这里的检查称为预约存量保护。

## 4. 明确调整锁协议

已有经营配置先取得店铺排他锁；早期预约草案却写成先锁日期保护行、再读锁配置。两者以后直接混用可能形成“一个持店铺等日期、另一个持日期等店铺”的死锁。建议本次明确调整该草案及 ADR-0017 对后续顺序的约束：**店铺作为统一前置协调行，然后锁日期保护行，再访问人员和时段等受保护资源。** 不是把两套相反顺序都保留。

- 配置写事务使用已有 shop 的 FOR UPDATE；本轮排班和营业时间保护都采用这个入口。多个日期保护行按 (barber_id, service_date) 升序获取。
- 未来创建预约等需要同时检查店铺配置和日期资源的事务，先取得店铺 FOR SHARE，再取得日期保护行 FOR UPDATE，并按统一顺序读取/锁定后续配置。不同日期/人员的预约可共享店铺读锁；配置修改会等待相关事务完成。
- 不允许未来交易沿用“已持日期锁后再申请店铺锁”的旧顺序；订单及其他影响占用的路径在实现时必须统一复核，不能仅凭本次配置测试声称已经完成交易锁协议。

这是用户本次已确认的早期锁顺序修改，替代旧的日期行先于店铺的草案。理由是复用当前店铺行作为一致的协调入口，避免枚举日期时遗漏并发新建排班，也不需要 Redis 或新的锁服务。代价是营业时间等配置写入会阻塞该店的预约事务；V1 优先简单明确的正确性，不能描述为已经测得性能优势。

本轮写入顺序：本人账号 → 当前会话 → 店铺 → 本人 OWNER → 日期保护行 → 理发师/时段；RC 写事务、锁后当前读。已有人员/服务配置写入继续由同一个店铺排他锁协调，本轮不自动删除其排班；预约接入前补齐停用/解绑等路径对有效预约的保护。读取排班用只读 RR，保证 date / 时段 / 人员版本来自同一快照。

## 5. 数据与事务范围

建议 V8 新增 barber_day_guard、barber_schedule，不修改 V1～V7；沿用 MyBatis-Plus、注解 SQL 与现有 merchant 分层，不增加基础设施。

- barber_day_guard：id、barber_id 外键、service_date，(barber_id, service_date) 唯一；用于没有订单时也能锁定同一天的协调行。
- barber_schedule：id、barber_id、service_date、start_at、end_at；(barber_id, service_date, start_at) 唯一，开始早于结束，按项目规范存 UTC。以 (barber_id, service_date) 外键关联保护行，防止出现没有保护行的排班；日期、时区、营业覆盖和重叠在应用事务中验证。

首次成功保存非空排班时，在店铺入口锁协调下建立该日期保护行；清空排班后保留保护行，不因没有时段而删除。GET 或从未配置日期的空集合无变化保存不建立保护行，也不增加人员版本。保护行创建时的父表外键隐式锁也必须在真实 MySQL 并发测试中验证，不能只画锁顺序图。

替换该日时段、建立必要保护行和增加人员版本是同一个事务。格式、窗口、权限、营业覆盖、旧版本、SQL 或会话失败都整体回滚；版本上限只允许无变化。未来查询可约时段不能仅检查保护行存在，还必须有有效排班、启用配置和无冲突占用。

错误沿用既有协议：认证无效 401；经营资格问题 403；PRINT 分类、非法字段/日期/时段、营业范围不满足为 400 / VALIDATION_FAILED；不可见人员为 404 / RESOURCE_NOT_FOUND；人员版本冲突为 409 / CONFIG_VERSION_CONFLICT；修改营业时间侵占现存排班为 409 / SCHEDULE_CONFLICT。失败不返回其他店铺的人员或排班信息。

1. 实现排班 GET / PUT 及 V8 两表迁移，补齐营业时间 PUT 的排班覆盖保护；可调用操作由 26 增至 28，完整规划仍为 62（34 个待开发）。
2. 真实 MySQL 验证当天/第 6 天/窗口外、校园时区与跨午夜等待、严格时间和 15 分钟对齐、4 段边界、相邻合并/重叠拒绝、午休、休息日、完整替换/清空及 UTC 往返。
3. 验证人员共享版本、无变化与上限、日期隔离、权限/归属、首次建保护行及清空后保留、实际 SQL 后异常回滚和会话过期；版本或失败不得留下半份排班。
4. 验证缩短/清空营业时间的保护，包含停用人员、过去日期与今天；并发保存排班和营业时间，提交结果始终相互兼容。
5. 同步 API 注解、运行 OpenAPI、完整规划、状态/数据库/决策文档及 Swagger / Apifox 点击指南。以上为验收要求，不代表已执行结果。

人工验收：理发商家登录 → 配置当天对应星期的营业时间 → 新建/选择理发师 → GET 指定日期 → PUT 分段排班 → 旧版本冲突 → 尝试缩短营业时间被拒 → 先调整/清空排班后再修改营业时间。排班尚不产生订单或可预约入口。
