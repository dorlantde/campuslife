# M08.5-A 有界发布优化方案

日期：2026-11-01。状态：**用户已明确采用，B/C已验证并收口**：[B的182项报告](reports/bounded-outbox-publishing-2026-11-01.md)、[C故障/对照报告](reports/outbox-publisher-comparison-2026-11-01.md)。C的11个真实JVM窗口及正式旧新各24轮通过，三档完整p95中位0.58～1.15秒、较旧异步降93.88%～96.95%，达到约定目标；写成本不减，非容量/HA或整体优于SYNC。批准记录见[ADR-0055](decisions/0055-bounded-outbox-publishing.md)。本方案针对[M08.4-B实测](reports/coupon-measurement-2026-11-01.md)的发布调度限制；以下推荐/确认措辞保留A阶段提案内容，实际交付以报告为准。既有协议见[ADR-0053](decisions/0053-reliable-order-messaging.md)、[ADR-0054](decisions/0054-async-coupon-claims.md)。

## 1. 问题与目标

当前`OutboxPublisher.scheduled()`在共享调度线程上每秒同步调用一次`publishOne()`；后者只认领一条，再发送、等待confirm并回写。B的健康样本每秒约发行1张、20张完整p95约19秒，采样积压19，定位到单条调度的等待。Broker发送仍在事务外，这项设计继续保留。

推荐一次小幅优化：**私有单工作线程，按条连续处理的小批次；每轮最多32次认领调用、最多1秒继续认领预算。** 去除健康积压必须逐秒等待的限制，同时将较长IO移出共享调度线程。批次是JVM工作配额，数据库仍逐条认领/回写，不批量占租约或合并事务。

目标是减少旧ASYNC的积压等待，并检验代价。不能预设优化后的ASYNC会快于SYNC，也不能预设可靠持久化写入会减少。仍保留默认SYNC与消息/券Redis关闭，前端继续暂停。

## 2. 源码依据与选择

| 当前源码 | 现状与约束 |
|---|---|
| [OutboxPublisher](../src/main/java/com/campuslife/messaging/service/OutboxPublisher.java) | 1秒fixedDelay、tryLock单次发送、停止后8秒等待；目前SQL/网络IO都占用调度回调 |
| [OutboxTransactions](../src/main/java/com/campuslife/messaging/service/OutboxTransactions.java) | 独立短RC claim/finish，30秒租约；重试1～60秒，最多20次 |
| [OutboxMapper](../src/main/java/com/campuslife/messaging/mapper/OutboxMapper.java) | LIMIT1 + FOR UPDATE SKIP LOCKED；回写限定messageId/PUBLISHING/leaseToken |
| [RabbitOutboxTransport](../src/main/java/com/campuslife/messaging/service/RabbitOutboxTransport.java) | 事务外网络、mandatory/return与correlated confirm；confirm等待3秒，不是总IO上限 |
| [CouponRedisRepairJob](../src/main/java/com/campuslife/coupon/service/CouponRedisRepairJob.java) | 已有私有单线程、SynchronousQueue与原子防重入的项目内先例，不影响Spring共享调度器 |

| 可选方式 | 取舍 |
|---|---|
| 共享调度回调内循环多条 | 改动少，但故障IO或多条发送会占住订单超时等共享调度，不推荐 |
| 私有单线程、有界小批次 | **推荐**；适合当前20条积压，保留每实例一次执行中的发送尝试，新增复杂度较少 |
| 多工作线程并发发布 | 可作未来候选，会增加在途、连接、DB竞争与关闭边界；本批缺少必要性证据，暂不采用 |

推荐方案不定义通用Executor/TaskScheduler Bean，不改消费者数、连接池、RabbitMQ拓扑或发布/声明连接隔离配置。

## 3. 待确认的具体参数

| 项目 | 推荐值与含义 |
|---|---|
| 自动唤醒 | 保留初始延迟1秒、fixedDelay 1秒；回调只检查开关并尝试提交一个工作任务，立即返回 |
| 工作线程 | 组件私有ThreadPoolExecutor，core=max=1；daemon线程，SynchronousQueue不存储待执行任务 |
| 防重入 | 原子标记限制一轮任务，拒绝策略AbortPolicy；忙/关闭或交接时拒绝则留待下个tick，不使用CallerRunsPolicy |
| 每轮上限 | 新配置候选`campuslife.messaging.publisher-batch-size=32`，仅允许1～32，非法值启动失败；每次claim调用计入配额，包括最后的空扫描 |
| 认领时间预算 | 固定1秒、System.nanoTime单调计时；每次claim前检查。不是本轮硬结束时间，已启动单条允许收尾 |
| 执行中尝试 | 每实例至多1条，包括原同步`publishOne()`与后台工作者；它们共用同一发送互斥 |
| 失败结束 | 第一条非ACK、条件回写失败、SQL异常或未知结果即结束本轮；每条原退避/20次上限保持 |
| 关闭等待 | 发布器自己的关闭流程共享一个8秒截止，包含锁等待及工作线程等待；不顺序等待两套8秒 |

消息与调度开关沿用原行为：消息关闭不得访问数据库/Broker；仅自动调度关闭时，原`publishOne()`仍可作为同步单次调用，且没有新增HTTP入口。执行器线程懒启动，组件关闭后不再接受任务。

`batch-size=1`可降低自动吞吐配额，但私有线程模型仍存在；它不等于恢复原二进制。完整回退需停旧进程后使用保留的原制品，按原租约恢复，保持相同数据格式。

## 4. 单轮流程与租约

```text
定时回调：
  消息/调度关闭或正在停止 -> 返回
  原子申请本轮资格 -> 向私有工作线程提交
  忙/拒绝 -> 释放本轮资格，下一次tick再试

工作线程：
  记录开始时刻
  最多32次：
    停止/中断/已过1秒继续认领预算 -> 结束
    尝试一次单条处理（保留共享发送互斥）
      未取到互斥/关闭/缺依赖 -> 结束
      短RC事务claim一条并提交30秒租约
      没认领到行 -> 结束
      事务外发送并等待结果
      独立短RC事务按原leaseToken回写
    只有ACK且条件回写成功 -> 可以继续下一条
    其他结果 -> 本轮结束
  finally释放本轮资格
```

原`publishOne()`的boolean不足以驱动循环：当前true包含NACK、TIMEOUT甚至leaseUpdated=false，不能直接写`while(publishOne())`。实现应在组件内部区分“ACK已落库可继续”与“已尝试但应结束／未尝试”；保持原单次调用契约，不为该结果增加公共接口或跨模块抽象。

**不预认领32条。** 每一条到实际执行时才调用原claim事务，上一条回写后再取下一条。否则后面的行在进程队列中等待也会消耗30秒租约，故障时容易跨租约重复发布。1秒预算使用在“是否继续认领”的位置，不能用它截断在途消息或据此猜测是否成功。

未知发送/提交结果不在catch中改回READY、清空租约或直接补写SENT；保留已提交事实及原条件恢复。ACK后finish=false意味着该租约没有成功回写，本轮停止并记录，不覆盖新持有者。旧PUBLISHING租约可能暂留，因此“当前只执行一条”不等于数据库里永远只有一行PUBLISHING。

`claim()`返回null还可能是原第20次租约到期后标DEAD，本方案仅结束当前轮，不宣称整张表已无待发消息。下一tick照原条件继续扫描。

## 5. 失败、关闭和混合路由

- Broker不可达、confirm超时、NACK或RETURN：先走原finish/退避，再终止本轮；不在故障时一口气对32条反复试发。不同新消息仍可能被后续tick认领，不新增全局熔断器。
- SQL认领或回写异常：本轮终止；提交是否成功以数据库事实为准。原30秒接管、messageId/正文不变、旧token失效与消费幂等继续负责重复，不承诺exactly once。
- 关闭先设置stopping并关闭任务提交，后续不开始新的单次尝试。关闭前已经进入的claim事务可能在请求关闭后提交，按唯一在途尝试处理，允许收尾；不作“关闭后绝不会新出现PUBLISHING”的过强承诺。
- stop幂等，不重新授予一套8秒。共享截止内等待互斥与私有线程；超过预算请求中断自有工作线程后返回。中断不是强制取消IO，在途结果仍可能迟到，原租约/条件写入提供恢复。直接调用`publishOne()`的外部线程不强制停止。8秒是发布器等待预算，不是整个应用或Broker交付SLA。
- 每轮有限且没有内存任务积压；较长IO发生在私有线程，不能拖住预约/打印超时的共享调度。SynchronousQueue在忙或任务交接窗口的拒绝只使本轮延后，业务事实仍在outbox。
- 通知与券命令继续共用原排序、LIMIT1/SKIP LOCKED和路由；不增加券专用优先级、配额、全局FIFO承诺或消费者并行度。混合路由必须回归，持续大量历史积压下仍可能等待，不新增未经定稿的公平调度规则。

## 6. 一次实现与验收拆分

以下B/C均待本次方案确认。分批是为了每次有明确验收终点，不代表额外开发业务。

**M08.5-B：实现与正确性回归。** 修改发布组件及一个批次上限配置；复用原claim/finish/transport，不改业务事务、DB schema、消息正文或消费者，不做SQL批量认领。补齐：

| 验证层 | 必须成立 |
|---|---|
| 组件边界 | 默认32/允许1～32；第32次后不再认领，1秒后不再启动下一条；空扫描/忙/关闭/异常结束；关闭开关无DB/网络；重复tick不排队、不在调用线程执行IO |
| 故障边界 | ACK+finish成功才继续；NACK/RETURN/TIMEOUT/连接失败/旧token/未知提交停止；非ACK不能被原boolean误判为可继续 |
| 关闭与在途 | 在途阻塞时仍只执行一条，其他新行保持READY；两次等待共用8秒、重复stop不延长，关闭前已进入认领的场景按文档收尾 |
| 真实MySQL/RabbitMQ | 两实例SKIP LOCKED、租约到期/旧结果拒绝/20次DEAD；原通知/券路由、return/nack、Broker停启与确认后重发、消费凭据/文件/订单兼容按风险选择回归 |
| 调度隔离 | 人为阻塞发布IO时，公共调度的哨兵及实际订单到期路径仍可执行；故障不会形成无界任务或大量预占租约 |
| 交付 | 保留未变的75操作/V23/32表；JAR启动、测试类未进入生产包、隔离资源回收与可复现指南 |

**M08.5-C：真实进程故障及一次同口径复测。** B正确性通过后，保留一轮故障/测量批次：

- 在测试类路径设停点，覆盖认领后发送前、confirm后SQL回写前、第一条SENT后下一条认领前；实际强杀自有JVM并重启。核对没有预认领整批，未结束租约可按原期限恢复，消息身份稳定、消费不重复生效。
- 复用M08.4-A相关真实JVM窗口；SQL精确租约边界可用测试Clock验证，但不能把时钟推进写成真实等待。8秒关闭由可控阻塞验证，并区分发布器与应用总关闭。
- **实现前保留当前生产classes/制品及依赖指纹**，不依赖未提交工作区的Git HEAD。用同版无mock测量驱动分别启动旧/新生产类路径，各执行现有24轮（每档三组配对、同样预热/补充/250ms轮询/25秒窗口），串行切换应用且先排空，无两个版本同时发布。旧/新类路径须完整隔离，禁止前后拼接导致新旧Bean混装。
- 归档版本顺序、原始样本与环境。版本分开执行有时序漂移限制，分别使用各自SYNC参照辅助识别；不据少量样本宣称普遍容量。`batch-size=1`只作配置回退检查，不冒充旧版本对照。

## 7. 目标、停止条件与确认范围

建议的健康本机性能验收目标：三档ASYNC完整获券p95的每档三轮中位数均**不超过5秒，且较同条件旧ASYNC降低至少70%**；它是本次优化是否有效的判据，不是业务SLA，也不要求胜过SYNC。无超发、重复券、错消息/旧token覆盖或资金/权限回归，未完成与技术错误不被丢弃。

同时完整报告全部POST／首次受理／最终成功、实际发行量、PENDING/outbox峰值、失败原因、GET数量、SQL/行锁/DML、CPU/堆与Redis成本。持久化协议不裁剪，20张的180次DML事实路径继续保留；采样窗内额外空扫描和GET减少分别说明，不能把总SQL变化全归为POST优化。

B允许修复发现的正确性缺陷；正确性通过后C只做一次固定参数对照，不反复调整线程、连接、批次或消费者追逐QPS。结果若未达到目标，保留失败/退化及原因，默认SYNC，按需回退制品后转原定对象存储/部署/材料方向；不自动增加多线程、Redis缓存或新组件。若发现会改变原协议的缺陷，先回到讨论边界。

本次请确认的是：**单私有工作线程／无任务积压、32次认领与1秒继续预算、失败结束本轮、总8秒关闭等待、B实现后C一次旧新复测，以及上述目标和停止条件。** 资金、优惠券有效期、5分钟处理、30秒租约、1～60秒/20次重试、业务/消费幂等与前端暂停均沿既定决定，不重新设计。
