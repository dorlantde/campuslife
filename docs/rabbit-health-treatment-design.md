# D.7.1-C RabbitMQ 最小处理提案

日期：2026-11-07原方案。当前2026-11-08：C.1实测缺客户端，原结果保持；用户已选择A，服务器依赖变更/C.2/集成/综合测量延后，先进入[M07材料与本人复盘](interview/project-evidence.md)。未构建新镜像或修改探针。下文保留原采用范围，不作为自动恢复服务器任务的授权。

## 1. 推荐与目的

推荐将**容器内、本机HTTP就绪检查**作为优先候选，先做C.1兼容关卡，通过后再实施和验证，最后才替换部署探针。原CLI保留为按需诊断工具。整个方案保持Docker探针总截止5秒、间隔5秒、retries30、start_period15秒及原资源限制；测量健康停止规则保持。

理由是本次已看到组合副本在有限CPU竞争下超过5秒；减少周期性CLI启动成本值得验证。它仍只是工程处理候选，不能称旧C.3根因已确定或已有性能收益。**采用提案只授权从C.1开始，后续按路线图逐项执行。**

C.1若发现固定镜像缺少合适客户端/总截止工具，或候选不满足故障判定，就停止该路线并保留原探针；增加镜像工具、秘密挂载或权限须另给具体提案。不用扩大超时、降低健康门槛或反复重跑原诊断来获得通过。

## 2. 已知、待验证与语义差异

已知：B.2的A窗口组合副本约2.740秒成功；B窗口组合副本5.006秒外层截止，第一段完成、第二段已开始但无结束标记。B按规则提前结束，认证矩阵、镜像客户端盘点未到达。该副本的宿主耗时不等于某条内段耗时；原探针两次-1仍UNKNOWN。[原始观察与限制](reports/rabbit-probe-observation-2026-11-07.md)。

| 选择 | 检查内容与局限 | 本次取舍 |
|---|---|---|
| 保留组合CLI | 应用运行及监听端口能接受TCP；串行调用共用5秒，不验证消息握手/账号或投递 | 当前继续生效；候选失败时保留，不自动加预算 |
| 仅ping、仅管理页200或仅TCP | 覆盖不到本项目需要的就绪状态 | 不作为替换方案 |
| 固定HTTP ready | 节点服务状态、AMQP/AMQPS监听、连接上限；请求管理监听也须可达 | 优先候选，需C.1/C.2证据后才替换 |
| 扩大CLI截止或放宽测量停止条件 | 改变原预算/门槛，仍保留周期性CLI成本 | 本提案不采用 |

CLI端口检查只验证TCP接入；固定4.3.6的ready实现检查服务状态、AMQP监听和连接上限，两者**覆盖不同**。HTTP ready不证明全部监听端口、应用账号认证、消息发布确认或消费成功；既有消息与发行事实核对仍承担这些验证，不用一个HTTP结果替代。[4.3 CLI手册](https://www.rabbitmq.com/docs/4.3/man/rabbitmq-diagnostics.8#check_port_connectivity) / [4.3.6 ready源码](https://raw.githubusercontent.com/rabbitmq/rabbitmq-server/v4.3.6/deps/rabbitmq_management/src/rabbit_mgmt_wm_health_check_ready_to_serve_clients.erl)。

这是明确的部署就绪信号调整，需用户采用，不宣称语义完全等价。单机部署以AMQP服务就绪为目标，Erlang分布式端口等不再由该高频信号逐端口覆盖；原CLI保留按需核查。

## 3. 候选契约

- 固定请求`http://127.0.0.1:15672/api/health/checks/ready-to-serve-clients`，不经代理、不重定向、不重试、不读用户客户端配置；只接受HTTP200和固定版本成功体的严格匹配。空体、未知格式、非200、超时及连接错误均失败，不把任意200当成功。
- 外层仍由Docker限制5秒；候选内部总工作截止拟4秒、终止宽限至多0.2秒，为启动/退出留余量。要求完整响应和子进程受限，不能只设置每次read/connect超时。正文上限4KiB，超限失败，失败日志只输出固定分类/状态码。
- C.1从**固定digest的实际镜像**确认curl或GNU wget、外层截止工具与所需shell能力。优先curl，次选经验证的GNU wget；C.1固定一种实现和绝对路径/版本/选项，正式脚本不在运行中自动切换客户端。不假设这些工具已经存在，不自行编写HTTP协议解析器或安装依赖。
- 候选拟不携带凭据，因此不新增密码挂载、不使用Cookie、不提升ops角色。固定ready源码未声明认证回调只是静态线索；C.1必须实测无凭据路径。若实测需要认证，则本提案的无秘密方案不成立，停止讨论，不把密码塞入命令行。
- 原`GET /api/vhosts?disable_stats=true`仅用于兼容验证的认证/归属对照：正常凭据200且精确名称一次，无/错误凭据拒绝。它不是每5秒探针的一部分，不做高频统计查询；不使用需要admin的单vhost GET。
- 拟新增一个只读挂载的部署检查脚本，继承现有探针执行身份，能力限于本机HTTP。业务JAR、依赖、数据库、MQ协议、资源上限、秘密及应用账号权限保持。

当前在线Docker Library 4.3分支已经指向4.3.7，不能据其Dockerfile或构建阶段的软件推定本机固定4.3.6镜像内的工具。本轮只查阅[官方镜像源码](https://raw.githubusercontent.com/docker-library/rabbitmq/master/4.3/ubuntu/Dockerfile)，没有盘点实际镜像。curl的整体传输截止与禁代理能力见[官方手册](https://curl.se/docs/manpage.html)；目标版本支持和子进程截止仍须实测。

## 4. 采用后的三个有限任务

| 阶段 | 范围及预算建议 | 完成标准与停止条件 |
|---|---|---|
| **C.1 固定镜像兼容关卡** | 一个新case，300秒含120秒清理。先做无网络、无秘密的短命工具盘点，再仅启动一个原Rabbit；不改原probe、不加CPU工作者、不启动业务六服务 | 核对固定digest/版本；容器内实际客户端请求ready；宿主ready与vhost两端点各正常/无/错凭据一次；确定客户端和无秘密方案可用。缺工具立即结束，不启动Broker凑结果；不符合契约则不进入C.2 |
| **C.2 隔离实现及故障验证** | C.1通过后下一项；一个新case，480秒含120秒清理。实现候选脚本与相关短检查，只在隔离test覆盖中生效，正式配置保持 | 下表全部必要场景有证据，内部截止/子进程退出/清理通过；部分或未知即未通过，不临时加预算或自动再跑 |
| **C.3 部署集成核对** | C.2通过后下一项；建立独立部署版本白名单，审核配置差异，复用原业务制品；不在旧release热改 | 只有审核过的部署脚本/配置及相应版本化测试入口变化；各mode/profile配置和回退路径核对通过，原release及历史失败保持。此项不自动包含原七服务测量验收 |

C.1工作上限180秒：工具/归属检查最多20秒、原Broker启动最多90秒、容器请求及六项权限对照最多40秒、证据退出最多30秒。相位结余不增加样本，缺失即按原回执结束。原480秒诊断的预算和结果没有被追改；300秒是新兼容任务的建议边界。

C.2的具体必要验证如下。测试故障只作用于已登记自有Broker/受控回环响应端，不改变宿主防火墙或其他实例。

| 场景 | 必须观察到的行为 |
|---|---|
| 正常与恢复 | 实际容器内脚本成功；每次故障解除后恢复成功，不靠旧响应/缓存 |
| Rabbit应用停止 | 使用原可信CLI做一次有界故障控制，候选非成功；明确确认应用确已停止，HTTP不可达也按失败处理；恢复后再成功 |
| AMQP监听缺失 | 在同一自有Broker用固定4.3.6已导出的监听停止操作制造故障；确认5672不可接入、管理HTTP仍通，ready必须失败；CLI控制未知或管理HTTP也不通不能冒充该场景通过 |
| 响应截止 | 用同镜像/同客户端、无秘密受控响应端模拟不返回及慢响应体；内部总截止和4.2秒内回收通过，Docker5秒作为外层保障；不能只杀docker客户端就声称子进程已退 |
| 错误响应 | 503/401/404、重定向、空体、非成功体、超限正文均拒绝；生产URL固定，测试地址覆盖仅存在于隔离辅助中 |
| 有限CPU竞争 | 原128MiB/单核/无网络60秒工作者，只保留一个候选窗口，在预定0/15/30/45秒检查四次；不运行手动组合CLI对照；核实工作者完整自退，不延长凑次数 |
| 资源与秘密 | 容器ID/cgroup/启动ticks/无OOM/秘密日志钩子及原账本清理完整；故障控制CLI超时或归属未知立即停止后续检查并按原ID清理 |

监听故障拟使用固定源码导出的`rabbit_networking:stop_tcp_listener/1`，它是一次测试控制而非高频探针；只限本case的既有5672监听。恢复通过原有界应用重启流程。实施须核对返回值和实际监听，不能仅凭调用名认定注入成功。[4.3.6网络实现](https://raw.githubusercontent.com/rabbitmq/rabbitmq-server/v4.3.6/deps/rabbit/src/rabbit_networking.erl)。

C.2不新增第二业务实例、新镜像下载、MySQL或消息交易；受控响应端/工作者均纳入原账本和工作总截止。480秒不足时保留未执行项并结束，不扩为长时间故障实验或性能比较。

## 5. 集成、回退和测量入口

只有C.2通过后才在新部署版本替换Rabbit healthcheck，保存原CLI配置作为可审核的回退。应用镜像/JAR可复用原指纹，不因探针脚本变化重构业务。旧三个release源、JAR、镜像与夹具全部保留。

现有资源辅助固定校验release/463输入/原探针；后续必须新增**明确指纹的新部署版本适配**，保留旧版本校验，而不是删掉源检查、忽略hash漂移或用任意挂载覆盖冒充正式配置。新增白名单项数以实际制品清单为准，本提案不先写成已生成新版本。

原测量HealthGate仍要求七服务身份/OOM/运行状态稳定、60秒健康基线、至少三个新完成成功结果、失败计数0；两个不同已完成失败结果仍停止。只为新配置记录实际探针身份和语义，不清空旧失败记录或放宽判定。

集成核对后，下一次独立任务再按原M06.2-B.2-C.3范围进行七服务验收，之后才能Pilot/正式逐批/M07。新探针若失败，回退或停止讨论，不自动恢复到无限诊断循环。不同探针下的结果标明版本，不与旧数据混合计算收益。

## 6. 采用后的关卡结果

用户已采用本提案并从C.1开始。固定4.3.6实际盘点无curl/wget，只有GNU timeout9.4和shell；按第1/4节停止，没有Init/启动Broker或执行HTTP矩阵。[C.1证据](reports/rabbit-health-compatibility-2026-11-07.md)。这并非原探针故障修复，也没有验证完整响应截止或无凭据权限。
