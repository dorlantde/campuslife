# 商家入驻与审核定稿提案

- 日期：2026-10-19（Asia/Shanghai）。
- 状态：2026-10-19 用户确认全部推荐方案并授权开发，见 [ADR-0010](decisions/0010-merchant-onboarding.md)。规则确认不等于所有接口已实现；当前交付见 [验收指南](merchant-onboarding.md)。
- 本轮范围：商家申请、申请人查看结果、管理员审核，以及受控创建平台管理员。
- 保持现状：单 Maven 工程、模块内分层、MyBatis-Plus 与注解 SQL、本机 VS Code 启动配置。
- 不在本轮展开：服务价格、营业时间、理发师与排班、订单、平台暂停店铺和完整账号管理。

## 1. 沿用已确认的身份基线

账号只拥有 STUDENT / MERCHANT / ADMIN 中一种角色，一个商家账号管理一家店，通过店铺成员关系表达归属。它们都是 account 表中的业务账号，与 MySQL root、campuslife 数据库连接账号无关。

学生注册继续固定创建 STUDENT，不接受客户端指定角色；普通资料接口不能修改角色。已有学生账号不会自动升级为商家。数据库和接口细化稿中的其他内容不能仅因已有字段就视为已经批准。

## 2. 申请与权限：已确认方案

| 项目 | 推荐行为 |
|---|---|
| 申请入口 | 独立的商家申请接口，不要求先注册学生；提交新的账号信息及店铺资料 |
| 账号规则 | 用户名、密码、昵称沿用已确认的账号校验与 BCrypt 策略；登录名在所有业务角色间唯一 |
| 申请资料 | username、password、nickname、categoryId、shopName、locationText，description 可选；不收真实证件、手机号或营业执照 |
| 店铺字段 | 名称去首尾空白后 1～80 Unicode 码点；位置 1～200；介绍最多 1000，首次未传或空白统一为空字符串；拒绝非法 Unicode 和未知 JSON 字段 |
| 分类与校区 | 基础分类先提供“理发”“打印”，通过迁移初始化；只能选择启用分类。分类为展示与筛选维度，不在本轮自动增加分类与服务类型绑定规则。校区固定 XINGHAI_MAIN |
| 初次提交 | 同一事务创建 ACTIVE 的 MERCHANT 账号、PENDING 店铺、PENDING 的 OWNER 成员；businessEnabled=false；任何一步失败整体回滚 |
| 返回 | 创建成功 201，返回账号 ID、店铺 ID、PENDING 状态；不自动登录 |
| 待审与被拒 | 可正常登录，使用本人资料、昵称、改密和退出接口，读取本人店铺与审核原因；不能管理服务、营业配置或订单 |
| 公开可见性 | 公开商家查询仅展示 APPROVED；PENDING 和 REJECTED 均不展示。审核原因只给本人和管理员查看 |
| 防止越权 | 身份与本人店铺从服务端会话和成员关系取得，不接受客户端指定角色、账号归属或审核结果 |

与账号 ACTIVE 不同，店铺 APPROVED 和成员 ACTIVE 决定经营权限。这样申请人能登录查看结果，同时无法绕过审核经营。审核状态变化由数据库即时决定，不要求更换 JWT 才生效。

## 3. 已选择：被拒后可修改重提

**已确认允许 REJECTED 的本人商家修改资料后重新提交，复用原账号和店铺。**

- 只修改分类、名称、位置和介绍；账号凭据通过现有认证与本人资料接口管理。
- PENDING 时不能修改或重复提交，避免管理员正在审核的资料被替换；本轮不提供主动撤回。
- 重提要求 expectedVersion，REJECTED → PENDING，shop.version + 1，成员保持 PENDING，营业开关保持 false。
- 保留历次审核记录，记录审核人、结论、原因、时间和被审核版本；清除当前店铺展示的上一轮审核结果，旧结果仍在历史记录中。
- APPROVED 不能再走申请重提入口，审核后的经营资料修改另随经营模块定义。
- 已定稿 POST /api/v1/merchant/shop/resubmit；只接收店铺申请资料与 expectedVersion，成功 200 返回当前本人店铺。

取舍：现有草案明确“不提供被拒后重提”。修改它需要增加一个接口及审核历史存储，但避免申请人因填错资料而必须换账号重新申请。用户已选择支持重提，旧限制不再适用。

## 4. 已选择：审核通过后默认停业

- 只有 ACTIVE 的 ADMIN 业务账号可查看申请列表、详情并批准或拒绝；学生和普通商家访问审核入口返回 403。
- 只审核当前 PENDING 店铺，必须携带读取到的 expectedVersion。
- 批准：PENDING → APPROVED，同事务激活 OWNER 成员并保存审核记录；店铺版本 + 1。
- 拒绝：PENDING → REJECTED，成员保持 PENDING，版本 + 1；reason 去首尾空白后 1～300 Unicode 码点，保存操作人与时间。
- 锁内复核操作者权限、会话、当前状态和版本；两个管理员同时审核同一版本，仅一个成功，另一个得到 409；旧请求重复发送也返回冲突，不重复写审核记录。

**已确认审核通过后仍保持 businessEnabled=false。** 通过审核表示获得经营资格；商家可在后续经营模块配置服务、价格和营业时间，再主动开启营业。APPROVED 店铺可在公开列表展示并标明停业，是否接收新订单由营业开关、营业时间和服务可用性共同判断。

另一选择是审核通过即 businessEnabled=true；它会让新店在尚未配置服务和营业时间时已显示启用，需要后续查询与下单分别处理这种状态。

## 5. 已选择：受控创建第一位平台管理员

**已确认提供显式执行的本机初始化命令，每次执行后退出。** 由使用者在本机填写管理员用户名、昵称和密码，按现有账号规范及 BCrypt 创建 ACTIVE / ADMIN 业务账号，执行后退出。

- 连接数据库仍使用 MySQL campuslife 专用账号；创建的是 account 表里的管理员，不创建 MySQL root。
- 不提供公开注册管理员的 HTTP 接口，也不在普通启动时自动创建默认管理员。
- 不内置固定密码，不将密码写入源码、日志或命令参数。
- 用户名已存在时拒绝创建，不把现有学生或商家账号改成 ADMIN，也不覆盖已有管理员密码。
- 本轮初始化用于本机人工验收；自动化测试独立创建自己的临时账号。

另一选择是本轮仅通过隔离测试账号验证审核功能，人工可用的管理员初始化稍后再做；这样用户暂时无法自行完成 Swagger 审核闭环。

## 6. 对现有设计稿的影响

用户已确认本方案；既有未涉及的业务规则仍保持讨论稿状态。

已记录 ADR，同步业务基线、数据库设计、状态迁移与接口契约，以及完整 OpenAPI 设计稿及生成器。规划目录由 61 增加到 62 个操作；三项交付依次新增三个申请/查询接口、四个审核接口和一个重提接口，当前 15 已实现，47 待开发，管理员初始化与审批见 ADR-0011，重提见 ADR-0012。

本轮仅确认上述入驻与审核范围。服务配置、排班、公开商家查询完整能力及订单按后续小任务分别开发，不因它们在完整规划中出现而一次全部实现。

## 7. 后续实现与验收顺序

1. 商家申请、基础分类和本人申请详情：使用 Swagger 申请、登录并看到 PENDING；重复用户名、非法分类、部分写入失败和越权需验证。
2. 管理员初始化及审批：使用两个业务角色完成批准或拒绝；验证版本冲突、并发审核与事务回滚。
3. 重提任务：拒绝后修改重提，保留原账号和店铺，历史审核记录可核查；验证待审重复提交、越权及旧版本请求。

各任务新增接口时同步提供运行时 OpenAPI 与 Swagger / Apifox 点击验收。权限与锁、回滚使用独立真实 MySQL 验证，不访问用户现有业务数据。角色校验不能仅凭“已登录”判断。
