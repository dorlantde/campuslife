# 公开理发师查询：已确认方案

- 日期：2026-10-21（Asia/Shanghai）。
- 状态：用户已选择“采用并实现”，见 [ADR-0020](decisions/0020-public-barbers.md)及[验收指南](public-barbers.md)。
- 推荐范围：实现已有规划的 GET /api/v1/shops/{shopId}/barbers，一个公开查询接口。预约空位、下单、评价和打印报价另行推进。
- 依据：[人员与绑定 ADR-0017](decisions/0017-merchant-barbers.md)、[按日排班 ADR-0018](decisions/0018-merchant-schedule.md)、[公开目录 ADR-0019](decisions/0019-public-shop-catalog.md)及[接口契约](v1-api-contract.md)。

## 1. 目标与已有决定

学生已经可以浏览商家及上架服务，本轮让学生选择服务后，能查看哪些人员提供它。理发师是店铺人员资料，不是登录账号。

沿用已确认的公开店铺资格：APPROVED + ACTIVE OWNER + 对应账号 ACTIVE / MERCHANT。店铺停业、分类字典停用、未配置营业时间不自动隐藏；不可见与不存在店铺统一 404。允许匿名或任意有效登录角色，携带失效 token 仍按已有认证规则失败。这些规则无需重新定稿。

以下人员展示、服务筛选和关联字段范围已由用户本次确认。现有管理端允许启用空绑定人员，也允许绑定下架服务，不能直接把管理端列表作为公开响应。

## 2. 推荐展示规则

| 场景 | 推荐行为 | 理由与影响 |
|---|---|---|
| 人员可见 | 本店 enabled=true，且至少绑定一项本店已上架 HAIRCUT 服务 | 不展示停用人员，避免学生选到无法提供任何公开服务的人员 |
| 绑定项目 | 只采用同店、HAIRCUT、enabled=true 的服务关系 | 不公开下架服务；两个独立外键不能保证同店，公开 SQL 仍须限定归属和类型 |
| 空绑定/仅下架绑定 | 人员从公开结果排除，不改动管理端数据 | 管理端仍可提前准备；服务重新上架后可恢复公开展示 |
| 无排班/休息日 | 仍可出现在人员目录 | 本接口不按日期筛选；人员目录与可约时段分开 |
| 手动停业/当前关门 | 合格店铺的人员仍可查看 | 沿用目录可浏览与实际接单分离的规则 |
| 可见 PRINT 店铺 | 未传 serviceId 返回 200 / OK、[] | 通用店铺页可调用同一路径，没有适用人员不必当作错误 |
| 无符合人员 | 200 / OK、[] | 区分“没有符合人员”与“目标店铺/服务不可见” |

人员启停、绑定增删或服务上下架在后续查询生效；查询不自动解绑、不修改人员版本，也不修复数据。数据库测试如人为建立跨店/错误类型关系，公开查询应忽略这类关系，不把其他店铺的服务 ID 暴露出来。

## 3. 接口与筛选

GET /api/v1/shops/{shopId}/barbers，shopId 为路径参数，serviceId 为可选查询参数。只精确放行此 GET，不放行 /shops/**、其他方法或尚未实现的 booking-slots。

两种 ID 都沿用规范正十进制 BIGINT 字符串，不能为 0、负数、前导零、空白、数字小数或溢出值；显式空 serviceId 也为 400 VALIDATION_FAILED。省略 serviceId 才表示不按某项服务筛选。

- 未传 serviceId：返回全部符合第 2 节条件的本店人员。
- 传入 serviceId：先按公开店铺资格检查店铺，再要求店铺为 HAIRCUT 分类、目标服务为本店已上架 HAIRCUT；不存在、跨店、下架或非理发服务统一 404 RESOURCE_NOT_FOUND，不区分具体原因。
- 对合法且可公开的目标服务，仅返回已绑定它的合格人员；该服务无人绑定时为 []。
- PRINT 店铺带 serviceId 同样执行上述规则，因此其打印服务不能作为理发人员筛选目标，返回 404；未传则按前表返回 []。

serviceId 是选择一个具体资源，目标不可见返回 404；与已有 serviceType 枚举筛选“合法类型但零匹配返回 []”含义不同。人员查询不能据此推断其他店铺的服务存在与否。

## 4. 响应范围

沿用统一 ApiResponse，data 为 PublicBarberView 数组，不新增分页。人员按 created_at DESC、id DESC，服务 ID 按数值升序；允许同名，不按姓名合并人员。

PublicBarberView 只返回 id、displayName、serviceIds，均使用已规划的字段。id 与 serviceIds 中每一项均为字符串；不返回人员版本、启停字段、账号/成员/审核信息、排班或内部关联记录。

serviceIds 表示该人员全部“本店已上架理发服务”的集合。即使使用 serviceId 筛选，仍返回这个完整公开集合，不把它截成只含筛选 ID；筛选决定返回哪些人员，不改变字段含义。学生可与已有公开 ServiceView 对照名称、价格与时长。

示例（ID 必须替换为实际数据）：

```json
[
  {"id": "302", "displayName": "模拟理发师乙", "serviceIds": ["201"]},
  {"id": "301", "displayName": "模拟理发师甲", "serviceIds": ["201", "202"]}
]
```

以上人员即使今天没有排班也可展示；响应不表示已预留服务、锁定价格或存在可预约空位。

## 5. 实现与一致性

复用 merchant 模块分层、公开店铺资格 SQL 和现有 barber/barber_service/service_item 表；沿用 MyBatis-Plus 与注解 SQL，不新增模块、依赖、XML、表或缓存。

采用只读 RR，将店铺资格、目标服务校验、人员启停与可公开绑定放在同一请求快照。并发停用/解绑/下架时，不把旧人员与新绑定拼在同一响应；已开始查询可返回其快照时的有效资料，下次请求看到新状态。不加写锁、不递增版本；未来创建预约仍须锁内重新校验资格、绑定、排班和占用。

以批量查询或联表取得人员与公开关系，避免逐人员查询服务。SQL 同时限定人员与服务归属及 HAIRCUT 类型，不仅在响应层隐藏字段。

## 6. 本次完成标准

1. 实现一个 GET，运行版由 31 增至 32 个操作；完整规划仍为 62 个，剩余 30 个待开发。其他待开发路径不提前开放。
2. 真实 MySQL + HTTP 验证匿名/有效与失效身份、公开店铺资格、停业/分类停用边界、PRINT 空结果及非法 ID。
3. 验证启停、空绑定、仅下架绑定、合法服务筛选、跨店/不存在/下架/打印服务的 404、完整公开 serviceIds、排序和同名人员。
4. 验证无排班仍可展示、关系归属/类型过滤、公开字段不泄露、批量读取及真实并发修改下的一致快照。查询不得修改任何配置。
5. 同步注解、运行 OpenAPI、完整规划、决策记录和 Swagger / Apifox 点击指南。以上是完成标准，尚不是已执行结果。

人工验收：准备已批准的理发店与两项上架服务 → 创建两名人员并绑定不同服务 → 启用人员 → 清除 Swagger 授权查询全部人员 → 填写实际 serviceId 筛选 → 商家下架一项服务/停用一人后重新匿名查询，对比公开展示。预约空位后续再实现。
