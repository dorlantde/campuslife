## 1. 推荐及要回答的问题

推荐先做一次 **D.7.1-B：单Broker、保留原Docker探针的480秒诊断**，把原探针输出的安全分类、两条CLI的分段证据、HTTP/TCP旁路观察和进程/资源放在同一case。诊断完即结束；没有足够解释力也如实交付，不自动追加样本或重跑C.3。

回答三个问题：原组合失败时实际记录是什么；诊断副本中耗时停在第一条、第二条还是宿主/exec环节；资源竞争与失败是否同时出现。HTTP候选只做兼容和语义调查，不在本项替换探针。不能以旁路HTTP成功直接证明原CLI误报或服务全面正常。

- 使用现有ECS上的**全新自有test case**，原B.1监督/原子回执和C.1资源账本；所有变更前登记，未知创建或Compose结果继续保守拒绝，不用空查询消除未知。
- 原release1cf0cb53a24a、正式JAR/镜像与六种基础镜像保持，Rabbit digest保持`sha256:54cb013d76cd1fd6c0a0708f34062ad61c452bb6f016b434c6c33f1a765d2b58`。不拉新镜像、在线安装软件、构建应用或上传整个工作区。
- 复用原showcase/compact4g Init及定义/私有目录，只启动Rabbit一个常驻组件。Init可能生成其余组件的原秘密/配置，但不启动MySQL、Redis、S3、应用、Nginx，不建业务库或发券/消息。
- 一个临时CPU工作者复用原应用镜像/JRE，只有独立诊断类，**128MiB、heap32MiB、CPU0且最多1核、无额外Swap、无网络、只读根、降权运行**，自行在60秒结束；不启动Spring。它只在第二窗口运行，不扩到内存/磁盘/网络压力。类由原JDK编译并先做无业务短验证，不改JAR/生产class。
- 原Rabbit探针/命令/环境/资源上限、Cookie、定义、权限和挂载保持。诊断HTTP由宿主读本case原运维密码并连接已验证的私网IP；不新增Rabbit秘密挂载或宿主端口，不扩大management账号标签/权限。

仅一个Broker加有限CPU竞争不等于原七服务现场，不以“未复现”宣布C.3或旧异常已修。临时工作者不是第二业务实例或性能负载。

## 4. 单次预算和固定观察安排

**总480秒，最后120秒只供清理；工作最长360秒。** 分阶段上限如下，阶段可提前完成，但不能把结余用于加样本或延长窗口。准备后剩余时间不够原计划即截断并报告，不能压缩清理。

| 阶段 | 上限 | 内容 |
|---|---:|---|
| 准备/本地短验证 | 45秒 | 固定输入/镜像/配置、账本/秘密生成；工作者编译/自截止与安全输出、身份/清理前置检查 |
| Broker启动/协议准备 | 90秒 | 只启动原Rabbit；验证原容器/卷/网络、固定版本、本case vhost与正常运维HTTP。记录从启动开始的原探针；入场不要求探针healthy，因为它正是被诊断对象 |
| 窗口A | 60秒 | 无附加CPU工作者，原Docker探针持续；固定手动诊断与HTTP/TCP旁路样本 |
| 窗口B | 60秒 | 同Broker、不重启，启动唯一60秒CPU工作者；其余观察安排与A一致 |
| 候选权限核对 | 45秒 | 工作者应已退出；对两个固定HTTP端点做正常/无/错误凭据各一次；盘点Rabbit镜像内现有客户端，禁止安装 |
| 证据与退出复核 | 60秒 | 原子写样本/分类/未执行项、日志泄漏检查、子进程与资源归属核对 |
| 清理预留 | 120秒 | 核对原ID/标签后回收工具、原Rabbit及自有卷/网络/秘密；失败回执不可改绿 |

每个60秒窗口预先固定：

1. 每秒最多一次宿主inspect，按容器ID＋Start/End去重保存**所有观察到的**原Docker探针；首5个在本窗口内结束的结果作预定对照子集。不足5个就记不足，不等第5个或挑成功样本；窗口外/跨界结果另列。读取失败/间隙也保留。
2. 在窗口相对第10/30/45秒各一次手动诊断：带安全阶段标记的原组合副本、单独check_running、单独check_port_connectivity。分别有**总5秒、5秒、5秒**外层截止，无自动重试；组合仍短路、共用5秒，不拆成两个5秒冒充原组合改善。单条检查仅定位，其各自预算不改变生产探针。
3. 在相对第0/20/40秒各一组HTTP/TCP观察：两个固定HTTP GET逐个执行、每个含完整响应体截止2秒/256KiB；AMQP 5672 TCP connect截止300ms。慢/缺失如实记，不积压队列，不补发错过时槽。
4. 每5秒采宿主及Rabbit/工作者cgroup CPU、内存、Swap、OOM和节流累计；区分缺失peak、采样最大值与内存上限，不称heap/RSS或容量。

“无工作者”仍有原探针及手动观察成本；手动CLI可能与原Docker探针重叠。保存重叠与时槽标签，不把样本说成纯空闲/独立实验，不把顺序A→B比较当因果证明。

## 5. 分段、超时和进程边界

**不修改原Docker healthcheck做埋点。** 原样本使用原Start/End/ExitCode/Output安全分类。额外的组合诊断副本只增加固定BEGIN/第一段结束/第二段开始/结束标记；单独CLI沿原gosu用户/Cookie/节点环境。时间记录宿主派发到返回，包含docker exec/标记传输开销；若无法取得可信内段时钟，就明确缺失，不能把宿主耗时当纯CLI耗时。

手动副本的阶段标记只支持“诊断副本在哪段未完成”，不能倒推某条未埋点的原Docker探针正是同一阶段。两次单独CLI也有顺序/热连接影响，不能简单相加就宣布原组合根因。

宿主在已验证的容器cgroup内采PID/start ticks/PPID/进程名，记录原Broker基线和手动wrapper的标识；不采完整argv/环境，以免Cookie泄漏。不靠进程名pkill。原探针与手动CLI重叠、权限不足或无法区分时标归属未知，不把所有新beam进程都算手动子进程。

**超时杀SSH/docker exec客户端不等于容器内进程已结束。** 手动检查超时后立即停止后续手动/竞争样本，最多5秒只读取证；不能证明子进程已退就结束专项并按原ID删除自有容器，使其cgroup整体回收，不继续污染样本。身份不明时拒绝定向发信号；资源清理失败按原回执保留，另做证据化处理。原Docker探针失败本身是待观察数据，不因它提前删掉这两个诊断窗口；OOM/容器退出等安全条件仍立即停止。

## 6. HTTP候选：调查语义和权限，不实施替换

固定4.3.6官方源码注册`/api/health/checks/ready-to-serve-clients`，其实现组合节点服务状态、AMQP/AMQPS监听与连接上限；这与原“全部监听端口TCP可接入”并不等价，也不验证账号认证或消费。[4.3.6路由](https://raw.githubusercontent.com/rabbitmq/rabbitmq-server/v4.3.6/deps/rabbitmq_management/src/rabbit_mgmt_dispatcher.erl) / [4.3.6检查实现](https://raw.githubusercontent.com/rabbitmq/rabbitmq-server/v4.3.6/deps/rabbitmq_management/src/rabbit_mgmt_wm_health_check_ready_to_serve_clients.erl)

该实现未声明`is_authorized`回调。**这是源码观察，运行权限行为尚未验证；不预设它必须认证。** 当前4.4 HTTP文档不是本镜像实测，4.3 HTTP手册本轮未能读取，不能用“通常API需要Basic”替代固定版本核对。

调查两个端点：上述ready端点，以及`GET /api/vhosts?disable_stats=true`作为认证/归属对照。正常凭据下要求后者200、响应为合法列表且本case精确vhost名称恰好出现一次；空列表/名称不符/重复或非法结构拒绝。无/错误凭据应被认证控制路径拒绝，不能把403当作节点停止。ready端点若无/错凭据仍200，应如实标记它不提供认证证明，而非宣称密码失效；若404/权限不足/缺字段，记候选不兼容，不改配置硬凑通过。

2026-11-07 B.1后修订：原已采用稿误选单vhost GET，固定4.3.6对此统一要求admin；原ops仅management，本轮实际返回401。列表资源普通认证并按可见范围筛选，不扩大账号权限。源码依据与失败见[B.1记录](reports/rabbit-probe-rediagnosis-2026-11-07.md)；原A快照保留。B.2已在真实Broker验证正常凭据列表200及精确名称；负面权限矩阵因截断未执行。生产probe和预算保持。

现有运维用户只有management标签，不增monitoring/administrator权限；不选择需要更高权限的`/api/nodes`作为强制成功条件。TCP端口可连接仅证明接受TCP，不能替代AMQP握手/认证。

只盘点固定Rabbit镜像是否已有可用HTTP客户端、可用超时/秘密输入方式。宿主HTTP可用**不证明容器内可直接做同样检查**。本轮不新增秘密挂载、不安装curl、不以`/api/overview`或任意200替代就绪语义，不停Broker应用/监听来做故障注入。若候选值得采用，后续另给具体差异、认证需求与停止/监听不可用/超时/恢复验证提案，仍保持总5秒；采用前不替换原探针。

## 7. 安全证据、完成标准与后续

探针Output先在宿主内存内处理：保留观测字节数、是否截断、严格允许列表的安全分类（如Docker明确超时标志、连接/认证/应用未运行/未知）及固定阶段标记。只在通过本轮秘密/JWT/Cookie类检查后保存有界指纹/规范化摘录；Cookie/hash、密码、Authorization、环境全集和任意诊断原文不进入日志/报告。无法安全分类的样本记UNKNOWN，不能清空Output后假装已定位。Docker原本就可能只存有限前缀，不把它称完整CLI原始输出。

允许的结果是“证据支持某种失败机制”“本次未复现”或“证据不足”。完成标准是每个预定时槽有记录/未执行原因、原探针与副本分开、超时/子进程/资源/权限有界且清理有凭证，并给出一个建议；**不要求探针全部成功或保证找出C.3根因**。截断/工具故障须列出，不能靠额外轮次拼齐。

实施拆分为：**D.7.1-B实现辅助、相关短检查和上述一次诊断 → 根据证据给出D.7.1-C最小处理提案（如有必要）→ 采用并验证后回C.3。** B不自动包含C、第五轮C.3、Pilot、SSH排障、公开/常驻实例。若没有解释力，交付未定因与下一步选择，不无限增加复杂度或把原测量门槛删掉。
