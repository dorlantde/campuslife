## 修复与诊断证据

1. **已修复部署兼容**：[mysql-init.sh](../../deploy/base/mysql-init.sh)用子shell隔离选项/变量，保留原SQL/权限/校验。两轮后续MySQL均健康，没有靠执行权限放宽或删校验解决。
2. **已修复监控兼容**：缺memory.peak明确为null，另记采样当前值；只对已过滤自有列表中明确消失的hex-ID做一次重列，其他异常仍失败。第3轮无监控错误，记录1次短时容器竞态重列。
3. **补齐测试就绪等待**：Resume前只读等待SQL/Redis代次/runId及暂停重建就绪，仍走原Inspect/版本校验，不改门闩、租约或Redis预算。第3轮两次等待32.969/2.230秒；复用已有快照减少两次重复CLI启动，不跳过交易断言。
4. **隔离诊断不等于根因已解**：原Redis客户端三次INFO成功1798/9/3ms；技术播种夹具的一次维护诊断捕获`CONTROL_VERSION_CHANGED`，证明后台推进版本与慢CLI启动存在竞争。但第2/3轮原Bootstrap只输出泛化失败，**两次泛化错误的底层原因仍未完整定位**。最后Resume的Bootstrap启动日志约53秒，不把它当HTTP接口延迟。

诊断类首次编译出现registerBean重载歧义，修正后才执行；编译失败前无组件产生。两个诊断入口仅挂载额外测试类、调用原Bean；未修改或重建生产JAR。维护诊断直接播种审核/门闩状态，明确仅为技术诊断，不计正式审核/订单验收。
