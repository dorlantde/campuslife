# 商家每周营业时间：已确认规则

- 日期：2026-10-19（Asia/Shanghai）。
- 状态：用户回复“采用并实现”，已确认全部规则。实现见 [ADR-0014](decisions/0014-merchant-business-hours.md)，实际验证见 [营业时间验收](merchant-business-hours.md)。
- 推荐范围：实现已规划的 PUT /api/v1/merchant/shop/business-hours，并让现有本人店铺查询返回真实营业时间；复用店铺权限和版本机制。

## 1. 与已确认规则的关系

ADR-0013 已确认 businessEnabled 独立保存商家营业意愿，商家可以先开启开关，未来接单仍须满足营业时间、服务及场景条件。配置营业时间不自动开启或关闭这个开关，也不改变审核资格。

现有设计稿提出按周配置、校园时区、不跨午夜、避免重叠。本提案细化这些规则供确认；尚未批准的排班、订单、节假日与平台暂停规则不随本提案一起生效。

## 2. 已采用规则

| 项目 | 推荐行为 | 理由与影响 |
|---|---|---|
| 权限 | 与经营 PATCH 相同：当前 ACTIVE / MERCHANT、本人 ACTIVE OWNER、APPROVED 店铺 | 未审核、被拒、成员停用或店铺被暂停时不能修改营业配置 |
| 配置模型 | 每周重复的营业计划；weekday 为整数 1～7，周一至周日 | 简单支持校园日常营业，暂不加入节假日或临时指定日期 |
| 时区与格式 | 固定 Asia/Shanghai，严格 HH:mm，精确到分钟 | 不随浏览器/服务器时区变化；营业时段不强制按预约的 15 分钟粒度对齐 |
| 区间 | startTime < endTime，不跨午夜；同日时段不能重叠 | 支持午休分段；不接受相同起止时间，也不把它解释成全天营业 |
| 时段数量 | 每天最多 4 段、整周最多 28 段，按原始请求计数 | 足够表达上午、下午、晚间等分段，并限制一次写入规模 |
| 休息日 | 没列出的星期表示休息；intervals=[] 清空整周时段 | 新店初始无时段，不预填虚构营业时间；清空时保留手动开关原值 |
| 保存方式 | PUT 完整替换整周配置，不是增量新增某一天 | 一次请求可原子保存整份计划；提交时必须包含所有希望保留的时段 |
| 相邻时段 | 允许首尾相接，保存前排序并合并为连续区间 | 09:00～12:00 与 12:00～18:00 等价于 09:00～18:00，避免无意义的重复版本变化 |
| 生效 | 保存成功后，用于之后的配置查询和营业判断，不重新审核 | 不改账号、分类、审核历史或登录会话；本项没有自动取消订单的行为 |

时间仅接受 00:00～23:59，不接受 24:00、秒、小数秒或时区后缀。因此本版不能表达跨午夜或恰好营业到次日零点的区间，夜间跨日需求以后单独扩展。原始时段重复也属于重叠，返回参数错误，不静默去重。

## 3. 接口与读取

PUT /api/v1/merchant/shop/business-hours，归属来自当前会话，不接收 shopId。请求示例：

```json
{
  "expectedVersion": "3",
  "intervals": [
    {"weekday": 1, "startTime": "09:00", "endTime": "12:00"},
    {"weekday": 1, "startTime": "14:00", "endTime": "18:00"},
    {"weekday": 2, "startTime": "09:00", "endTime": "18:00"}
  ]
}
```

这个例子只有周一、周二营业，周三至周日休息。若原来其他日有时段，本次会删除它们；版本必须替换为 GET /merchant/shop 的实际字符串版本。

- expectedVersion 必传，沿用规范非负十进制字符串与 BIGINT 范围；不接受数字、null、空白、前导零或溢出。
- intervals 必传，且必须为数组；null、遗漏、非对象元素、未知字段均拒绝。每项严格包含 weekday、startTime、endTime，不接受客户端 ID 或归属字段。
- weekday 必须为 JSON 整数 1～7，不接受字符串、布尔值或小数（例如 1.0）。时间必须为严格字符串；不自动补零、去空白或纠正错误时间。
- 先检查原始请求数量和各项格式，按 weekday/startTime/endTime 排序；同日重叠或重复返回 400 / VALIDATION_FAILED；首尾相接的合法区间合并后保存。
- 成功 200 / OK，返回现有 MerchantShopView，增加 businessHours 数组；数组按星期、开始时间升序，空配置返回 []。
- GET /merchant/shop 同步返回真实 businessHours，不增加独立 GET 接口。使用同一店铺返回模型的修改、重提和管理员查询也要返回真实配置，不能为旧接口填假空数组。PENDING / REJECTED 仍按现有权限读取自己的信息。

本项不新增 openNow 字段。后续公开查询实现时，“当前在营业时段内”按左闭右开判断：09:00～12:00 在 09:00 开始包含，在 12:00 结束不包含；还要同时满足店铺/成员资格和手动开关。是否能为某项服务接单仍需独立检查，不能把时段匹配当作预约资源预留。

## 4. 版本与事务

营业时间与店名、位置、介绍、营业开关共用 shop.version。请求版本过期时，即使提交相同时间也返回 409 / CONFIG_VERSION_CONFLICT；资料修改和营业时间保存不能互相覆盖。

比较排序、合并后的配置。实际变化才整周替换并将 shop.version 加一，无变化不写 SQL、不增加版本，但仍检查权限、状态、会话和版本。BIGINT 上限允许无变化读取，拒绝实际修改，沿用已确认的经营 PATCH 规则。

计划新增 V4 迁移建立 shop_business_hour：shop_id 外键、weekday、start_time、end_time，(shop_id, weekday, start_time) 唯一，并以 CHECK 校验星期和合法同日区间。历史 V1/V2/V3 不改写。数据库约束负责基本合法性，同日重叠由持有店铺锁的事务检查。

锁顺序沿用本人账号 → 当前会话 → 店铺 → 本人 OWNER → 营业时段；先锁店铺再合并比较、删除旧时段并插入新时段、更新店铺版本，统一提交。任一步失败整体回滚，写入前复查会话到期。读模型中的版本和时段使用一致事务读取；锁后合并不能使用等待前的旧快照。管理员分页需要批量读取对应店铺时段，避免为每家店单独追加一次查询。

权限/错误沿用经营接口：认证失效 401，非商家/账号停用/店铺未批准或成员无效 403，无本人店铺 404，格式/区间/数量错误 400，版本冲突 409。

## 5. 完成标准与后续边界

本轮落实一个已规划 PUT，运行操作由 16 增至 17，完整规划仍为 62；同步 Java 注解、运行导出、完整规划与 Swagger / Apifox 点击指南。人工验收为：批准商家 → 登录 → GET 版本 → 保存午休分段 → GET 查看 → 同配置不加版本 → 旧版本冲突 → 清空为 []。

独立真实 MySQL 计划覆盖权限、时区/严格类型、星期和时间边界、重叠与相邻合并、数量上限、顺序变化的无变更语义、清空、版本上限、与经营 PATCH 并发、删除/插入中途失败回滚，以及会话/状态锁后复查。以上为验收要求，实际执行结果以营业时间验收指南为准。

当前没有理发师排班、预约占用或订单表，所以本项只验证营业时间配置。后续引入这些模块前，需要定稿并接入“修改营业时间不能破坏已有有效预约”的保护与统一锁协议；不能仅凭本项测试宣称有存量预约时也安全，也不能静默取消预约或订单。

本项不扩展节假日、跨午夜营业、临时指定日期、排班或订单补偿。后续建议定稿服务配置，再逐步接入具体场景。
